## ขุนคลัง Obsidian Full-Context "Agent" (พำนักที่ไฟล์ `obsidian_fullcontext.py`)

**ชนิดพนักงาน:** สายยิงตรงหา Gemini (ไม่ได้ปั้นคลาสเป็น `Agent()` แบบของ CrewAI)
**วิธีหาเสบียงข้อมูล:** มันจะไปควานหาอ่านโน้ตมาจากตาราง **`obsidian_notes` (ใน PostgreSQL)** — ถ้าผู้ใช้ถามเจาะจงจังหวัด ก็จะกรองดึงมาเฉพาะของจังหวัดนั้น (กินพื้นที่ราวๆ ~100–200 KB) แต่ถ้าถามหว่าน ก็จะหอบมาทั้งคลัง vault เลย (ขนาดบิ๊กเบิ้ม ~1.1 MB) โดยมีสวิตช์เบรกเกอร์ตัดบทที่ `OBSIDIAN_MAX_CONTEXT_CHARS = 500000` (ตัดตัวอักษรส่วนเกินทิ้งกันเซิร์ฟระเบิด)

### เจาะลึกคาถาสะกดจิต (SYSTEM_PROMPT) — สรุปใจความสำคัญ
> *"คุณคือศาสตราจารย์ผู้เชี่ยวชาญด้านข้อมูลสุขภาพ ประจำเขตสุขภาพที่ 10 (ครอบคลุม อุบลราชธานี, ศรีสะเกษ, ยโสธร,
> อำนาจเจริญ, มุกดาหาร) ... กติกาเหล็กคือ ขอให้ตอบโดยอ้างอิงเนื้อหาจากเอกสารที่เราแนบไปให้เหล่านั้นเท่านั้น"*

**แม่พิมพ์รูปแบบคำตอบที่ถูกบังคับ (สไตล์ Markdown):**
1. **ส่วนสรุปคำตอบ** — ขอแบบเนื้อเน้นๆ 2–3 ประโยค ตอบตรงประเด็นไม่อ้อมค้อม
2. **ส่วนข้อมูลจากคลังความรู้** — ถ้ามีตัวเลขให้งัดมาโชว์ในรูปแบบ ตาราง/หรือลิสต์รายการ
3. **ส่วนบริบทและการวิเคราะห์** — ขอแง่มุมวิเคราะห์เชิงลึกสัก 2–3 ประเด็น

**กฎเหล็กแห่งความทนทาน (ความสามารถ + สิ่งที่ห้ามทำเด็ดขาด):**
- ต้องหยิบคำตอบมาจากเนื้อหาในเอกสารล้วนๆ — **ห้ามเสกตัวเลขขึ้นมาเองเด็ดขาด** (No Hallucination)
- ถ้างมหาในคลังแล้วไม่เจออะไรเลย → ให้สารภาพบาปไปว่า *"ไม่พบข้อมูลในคลังความรู้"* + พร้อมเสนอแนะคำใบ้คำค้นหาใหม่ๆ ให้ผู้ใช้
- **ต้องเปลี่ยนเลขปี ค.ศ. → กลับมาเป็น พ.ศ. เสมอ** ให้คนไทยอ่านง่าย
- ห้ามพิมพ์หัวข้อ "แหล่งข้อมูล" แปะมาในคำตอบ (เดี๋ยวระบบแอปจะเสกโชว์ป้าย `notes_referenced` แปะท้ายลิงก์ให้เอง)
- กรณีที่มี "ประวัติแชทความหลัง" แนบไปด้วย → ต้องทำตัวเนียนๆ ตอบสานต่อเป็นเรื่องเดียวกัน (ถ้าเป็นคำถาม follow-up ก็ขอให้ตอบสั้นๆ ชี้เป้าเฉพาะจุดที่เขาสงสัยเพิ่ม ไม่ต้องร่ายยาวใหม่หมด)
- 🆕 **หมวด "ห้ามเด็ดขาด (anti-leak)"** — ห้ามคัดลอกเนื้อหาดิบของเอกสารต้นฉบับมาแปะ ไม่ว่าจะเป็นบรรทัดที่ขึ้นต้นด้วย `FILE:`, บล็อก YAML frontmatter (ข้อความคั่นด้วย `---`), wikilink `[[...]]` หรือเลขหน้า/หัวกระดาษดิบ — **ต้องเรียบเรียงใหม่ด้วยคำพูดของตัวเองเสมอ**
- 🆕 **บังคับปิดท้ายด้วยบล็อก machine-readable** (แทนที่ของเดิมที่แค่ "ห้อยท้ายคำถาม 2–3 ข้อ" ลอย ๆ):

```
<<<FOLLOWUPS>>>
["คำถามติดตาม 1?", "คำถามติดตาม 2?", "คำถามติดตาม 3?"]
<<<END_FOLLOWUPS>>>
```

  กติกา: ต้องเป็น JSON array ของสตริงล้วน 2–3 ข้อ แต่ละข้อเป็นประโยคคำถามสั้นลงท้าย `?` ห้ามมีตัวหนา `**` ห้ามมีหัวข้อ และ**ห้ามมีข้อความอื่นตามหลังบล็อกนี้อีก**

> [!bug] 🆕 ทำไมต้องเปลี่ยนมาใช้บล็อก JSON
> ของเดิม `_extract_follow_ups()` ใช้ regex เดาว่าอะไรคือ "รายการเลขข้อ" ในคำตอบทั้งก้อน → มันดันไปหยิบ **หัวข้อ markdown ของคำตอบเอง** มาแสดงเป็นปุ่มคำถามแนะนำ ผู้ใช้เลยเห็นปุ่มเพี้ยน ๆ อย่าง `**สรุปคำตอบ**` กับ `**ข้อมูลจากคลังความรู้**` — ตอนนี้ `_extract_and_strip_followups()` อ่านจากบล็อกที่ระบุตำแหน่งชัดเจน แล้ว**ตัดบล็อกนั้นออกจาก content ก่อนส่งให้ผู้ใช้เห็น** พร้อมกรองซ้ำอีกชั้น (ต้องลงท้าย `?`, ยาว 5–160 ตัวอักษร, ห้ามมี `**` หรือขึ้นบรรทัดใหม่)

### 🆕 ด่านกันเนื้อหาดิบหลุด (Anti-leak guard) — 3 ชั้นซ้อน

เคยเจอของจริง: คำถามกว้าง ๆ อย่าง **"มีเอกสารอะไรบ้าง"** ทำให้ Gemini คัดลอกบล็อก `## FILE: ...` พร้อม YAML frontmatter และ wikilink ทั้งดุ้นมาเป็นคำตอบ

| ชั้น | กลไก | เกิดตอนไหน |
|---|---|---|
| 1 | หมวด "ห้ามเด็ดขาด" ใน `SYSTEM_PROMPT` | ก่อนตอบ |
| 2 | **เบรกมือระหว่างสตรีม** — เฝ้าหาง 400 ตัวอักษรของบัฟเฟอร์ ถ้าเจอร่องรอย → หยุดยิง `obsidian_chunk` ทันทีกลางคัน (แต่ยังสะสมข้อความต่อจนจบ ส่งให้ชั้น 3) | ระหว่างเขียน |
| 3 | `_contains_leak()` ตรวจทั้งก้อน → ถ้าเจอ **retry ด้วยพรอมต์เข้มขึ้น** (`_LEAK_RETRY_SUFFIX`) → ถ้ายังหลุดอีก `_strip_leaked_blocks()` ตัดทิ้งเองแบบ best-effort | หลังได้คำตอบเต็ม |

🧪 ทุกชั้นมีเทสต์คุมใน `tests/test_obsidian_fullcontext.py` รวมถึง golden-set ที่จำลอง Gemini ตอบเนื้อหาดิบหลุดแล้วยืนยันว่าผู้ใช้ไม่มีวันเห็นเนื้อหาดิบเป็นคำตอบสุดท้าย

### 🆕 สตรีมคำตอบสด (`on_delta`)

`_call_gemini()` รับพารามิเตอร์ `on_delta` เพิ่ม — ถ้าส่ง callback มาจะเปลี่ยนไปใช้ `litellm.completion(stream=True)` แล้วยิง token ทีละก้อนกลับไป ผู้เรียก (`analyze.py`) ส่ง callback ที่แปลงเป็น SSE event `obsidian_chunk` เหตุผลคือคำถามสายนี้กินเวลา **~50-60 วินาที** เดิมผู้ใช้นั่งรอหน้าจอเงียบ ๆ จนจบ

### 🆕 ยุบอ้างอิงให้เหลือ 1 เอกสาร = 1 ลิงก์

ไฟล์ PDF ยาว ๆ ถูกตัดแบ่งเป็นหลาย `.md` ตอน ingest (`...-ส่วนที่01`, `...-ส่วนที่02`, ..., `...-INDEX`) ทุกส่วนชี้ `file_id` เดียวกันใน MinIO — เดิมป้ายอ้างอิงจึงโผล่ซ้ำ **15-20 ป้ายของเอกสารเดียวกัน** ตอนนี้ `_clean_doc_title()` (ใช้ `_PART_SUFFIX_RE`) ตัดคำต่อท้ายออก แล้ว dedupe ด้วย `file_id` (ส่วนที่ไม่มี PDF ผูกอยู่ใช้ path ตัวเองเป็นคีย์แทน)

### ผลผลิตที่คายออกมา (Output)
ปั้นก้อนร่าง `ObsidianAskResponse(content, notes_referenced[], follow_ups[])` — แล้วแปลงเป็นสายน้ำสตรีมพ่นกลับไปหาเบราว์เซอร์ผ่านท่า SSE

> [!important] 🆕 `notes_referenced` ไหลเข้ารายงานได้แล้ว
> เดิมโหมดสร้างรายงานเก็บแค่ `.content` ทำให้เอกสารคลังความรู้ไม่มี URL ติดไปกับรายงานที่สร้าง (ต่างจาก ThaiJo/PubMed/Tavily) ตอนนี้ `analyze.py` ส่ง `notes_referenced` ต่อผ่าน `_obsidian_notes_to_articles_text()` แล้ว — ดู [[06 - Report Generation Workflow]]

### สรุปรวมขีดความสามารถ
| ด้านความเก่งกาจ | รายละเอียด |
|---|---|
| สายค้นหาเป้าหมาย | มีระบบตีคะแนนความเกี่ยวข้อง `_relevance_score` (คำนวณจากน้ำหนักคีย์เวิร์ด × ความลึกของ path) เพื่อคัดโน้ตเด็ดๆ ก่อนโหลดไปให้ AI อ่าน |
| สายโต้ตอบ | Gemini โชว์พลังสมองอ่านเนื้อหาเต็มๆ (context เต็ม) → ย่อยมาเป็นโครงคำตอบ 3 ส่วน + แปะแหล่งที่มาของโน้ต + แนะนำคำถามล่อเป้า follow-ups |
| สายกันการมั่วเพ้อเจ้อ (hallucinate) | ตรึงพฤติกรรมบังคับให้ลอกคำตอบมาจากเอกสารเท่านั้น + พกยันต์ `dedupe_repeated_answer` กันอาการ AI เมากาวตอบประโยคเดิมซ้ำๆ |
| 🆕 สายกันเนื้อหาดิบหลุด (anti-leak) | ด่าน 3 ชั้น: พรอมต์ → เบรกมือระหว่างสตรีม → guard+retry+ตัดทิ้ง (🧪 มีเทสต์คุมครบ) |
| 🆕 สายสตรีมสด | `on_delta` callback → SSE `obsidian_chunk` ลดเวลารอที่ผู้ใช้รู้สึกจาก ~50-60 วิเงียบ ๆ |
| 🆕 สายจัดระเบียบอ้างอิง | `_clean_doc_title()` + dedupe ด้วย `file_id` → 1 เอกสารต้นฉบับ = 1 ป้ายอ้างอิง (เดิมโผล่ซ้ำ 15-20 ป้าย) |

> [!note] จุดแตกต่างจากช่องทาง Search API แบบปกติ
> ต้องแยกให้ออกนะครับว่าปุ่มแชทหน้าจอนี้ใช้วิชา "full-context" (เหมาเนื้อหาโยนให้ Gemini อ่านทั้งก้อน) — แต่ถ้าไปมุดใช้ช่องทาง `POST /api/obsidian/search`
> อันนั้นจะไปปลุกตัว `tools/obsidian.py` ให้ทำงานด้วย **pg_trgm ซึ่งสืบค้นด้วยสคริปต์เพียวๆ ไม่ใช้พลังของ LLM เลยแม้แต่น้อย** (ใช้ท่า Tier1 หาเป็นก้อน chunk + ไต่ตาม wikilink, ถ้าไม่เจอค่อยงัดท่า Tier2 สาดเวทมนตร์ LIKE หาคลุมๆ)
> แวะไปดูเชิงลึกต่อที่ [[03 - Knowledge Vault Workflow]] และผังดาต้าที่ [[04 - Data Architecture & Schema]]
