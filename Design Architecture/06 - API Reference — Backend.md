# 📡 คู่มืออ้างอิง API ฝั่ง Backend (ของโปรเจกต์ `chatapi.python`) แยกจำแนกตามรายไฟล์

← [[05 - File Structure Tree]] · อ่านควบคู่กับ → [[07 - API Reference — Frontend (BFF)]] · อ้างอิงสเปกเดิม: [[04 - External Interface Requirements]]

> เอกสารชุดนี้ถูกจัดทำขึ้นมาเพื่อไล่อธิบายเจาะลึก **ระบบสั่งงาน API ทีละเส้น ทีละไฟล์ในส่วนของตัวรับแขก router** (ที่อยู่ในโฟลเดอร์ `src/routers/*.py`) แกะแบบมาจากโค้ดต้นฉบับจริงทุกบรรทัด
> (เช่นการแปะป้ายตัวสัญลักษณ์ decorator `@router` + รูปแบบ Pydantic schema) — จัดเรียงระบุชนิดการเรียก Method, เส้นทาง Path, สิ่งที่ต้องส่ง Request, สิ่งที่ตอบกลับ Response และหมายเหตุข้อควรระวัง
> **ข้อมูลฐาน URL ที่ควรรู้:** `http://python-ai:8000` (เป็นชื่อเรียกกันในเครือข่ายภายในคอนเทนเนอร์) / หรือ `http://localhost:8000` (หากรันจากฝั่งคอมพิวเตอร์ dev) · ส่วนหน้ากากชี้เป้า Swagger ลองไปที่: `/docs`
> **คำเตือนตัวโตๆ (สำคัญสุด):** ชาวบ้านผู้ใช้ทั่วไปหรือหน้าเว็บฝั่งนอก จะกระโดดมาเรียกตรงๆ ไม่ได้เลย โดนบล็อกแบนสนิท ต้องตีตั๋วผ่านประตูหน้าด่าน BFF เพื่อให้สวมหน้ากากแนบรหัสลับ `x-internal-key` มาให้เท่านั้น (อ่านเพิ่มที่ [[07 - API Reference — Frontend (BFF)]])

รูปแบบการตอบกลับพ่นน้ำลายของระบบที่พบบ่อยๆ: 
- ท่า **SSE** = ตอบเป็นสายธารข้อมูลสตรีม `text/event-stream` (จะไหลแจ้งจังหวะหายใจของโมเดลผ่านชื่อ event ว่า `agent_start` รอเกิด / `agent_done` ทำเสร็จจุดนึง / `text_chunk` แหว่งข้อความออกมา / `result` สรุปกลางทาง / `final` สรุปจบบริบูรณ์ / หรือ `error` ร่วงตาย) 
- ท่า **JSON** = ตอบฟรึ่บ โยนออกมาเป็นก้อนตู้มเดียวจบ

## 1. `analyze.py` — ด่านปราการประตูหน้าหลักของระบบแชท (tags: analyze)

| วิธีเรียก (Method) | เส้นทางระบุ (Path) | สิ่งที่ต้องป้อนมา (Request) | รูปแบบผลลัพธ์ (Response) | หมายเหตุ / ข้อควรระวัง |
|---|---|---|---|---|
| GET | `/health` | — | คืนค่าดิบ `{status: "ok"}` | ใช้เปิดไว้เผื่อทดสอบเช็คชีพจรว่าเซิร์ฟยังหายใจอยู่ไหม (health check) |
| POST | `/api/analyze` | โยนร่างก้อน `AnalyzeRequest` | **ตีกระจายสตรีม SSE** | ท่านายพลใหญ่ orchestrator คุมคิวหลัก: รับทำคิววงจร Memory→ชี้เป้าRouter→ดันเข้าท่อpipeline |
| POST | `/api/chat` | โยนร่างก้อน `AnalyzeRequest` | **ตีกระจายสตรีม SSE** | ตั้งชื่อแฝง (alias) เลียนแบบทำตัวเหมือนเส้นทางของ `/api/analyze` ทุกประการ |

**เจาะไส้ในของก้อน `AnalyzeRequest`:** ระบุชื่อห้อง `sessionId: str` · ส่งประโยคคำถามมาที่ `prompt: str` · โยนลิสต์ประวัติเก่ามาเผื่อด้วยที่ `history: [{role,text}]?` ·
สั่งลุยในโหมดไหน `mode: str = "normal"` (ตัวเลือกเช่น `normal` โหมดชิวๆ \| `stats` โหมดโหดสถิติ \| `obsidian` โหมดห้องสมุด \| `tavily` โหมดออกเน็ต \| `multi` สั่งผสม \| `research` โหมดวิชาการ \| `report-gather` โหมดซัดเต็มเหนี่ยวรวบรวมรายงาน \| 🆕 `report-gather-retry` โหมดลองใหม่เฉพาะแหล่งเดียว) ·
และอาจพ่วงของเล่นมา `tools: str[]`

**🆕 3 ฟิลด์ที่เพิ่มเข้ามาใหม่ (ทั้งหมด optional — ใช้เฉพาะสายสร้างรายงาน):**

| ฟิลด์ | ชนิด | ใช้ตอนไหน | ทำอะไร |
|---|---|---|---|
| `doc_type` | `str?` | `mode=report-gather` | ชนิดเอกสารที่ผู้ใช้เลือกไว้ **ตั้งแต่ก่อนเริ่มระดมข้อมูล** (`policy`/`plan`/`workplan`) — backend ไม่ได้เอาไปใช้คิดอะไร แค่ **echo กลับใน event `final` เป็น `docType`** เพื่อให้ wizard ฝั่งหน้าจอข้ามขั้นตอนถามซ้ำว่าจะทำเอกสารประเภทไหน |
| `retry_source` | `str?` | `mode=report-gather-retry` | ชื่อแหล่งเดียวที่จะรันซ้ำ — รับได้แค่ 5 ค่า: `obsidian` \| `stats` \| `thaijo` \| `pubmed` \| `tavily` **ถ้าส่งค่านอกนี้มาจะได้ event `error` กลับทันที** ไม่ใช่ 4xx |
| `report_title` | `str?` | `mode=report-gather` | ชื่อเรื่องสั้น ๆ ที่ผู้ใช้พิมพ์จริง — แยกออกจาก `prompt` ที่อาจถูกเสริมด้วยหัวข้อที่เลือกไว้ล่วงหน้าจนยาวเป็นพืด ถ้าไม่ส่งมาจะ fallback ไปใช้ `prompt` ตามเดิม (กันชื่อรายงานยาวเฟื้อย) |

> [!info] 🆕 `report-gather-retry` ทำงานยังไง
> ใช้ **โค้ดเส้นทางเดียวกันเป๊ะ** กับ `report-gather` ต่างกันแค่จุดคัดเลือก worker: ปกติรันทั้ง 5 ตัวพร้อมกัน (ทยอยปล่อยห่างกัน ~1.5 วิ กันชน 429) แต่โหมด retry จะเลือกมาแค่ตัวเดียวตาม `retry_source` และ**ไม่หน่วงเวลา**เพราะไม่มีใครให้ชน — ประหยัดเวลา + ไม่ยิง LLM ซ้ำกับแหล่งที่สำเร็จไปแล้ว ผลลัพธ์กลับมาใน `final` พร้อมฟิลด์ `retrySource` เพื่อบอกหน้าจอให้ **ต่อท้าย** ไม่ใช่เขียนทับ

> [!tip] 🆕 UX nudge: คำถามอุบัติเหตุที่ไม่ได้กดปุ่ม "สถิติ"
> ถ้า router จัดคำถามเข้าโดเมน `d1` (อุบัติเหตุ) ในโหมด `normal` ระบบจะ **เปลี่ยนเส้นทางไปตอบจากคลังความรู้ (Obsidian) แทน** เพราะผู้ใช้ไม่ได้เลือก stats tool จึงไม่ควรปลุก Accident SQL Agent — และจะ **แปะหมายเหตุนำหน้าคำตอบ** เตือนว่าตัวเลขนี้มาจากรายงานที่บันทึกไว้ (ไม่ใช่ query สดจาก DB) พร้อมชวนให้กดปุ่ม "สถิติ" ถ้าอยากได้ตัวเลขปัจจุบัน
**กลไกความโหด:** แอบตั้งเพดานขีดจำกัดด้วยยันต์ `BoundedSemaphore(5)`/ต่อเวิร์กเกอร์ — หมายความว่าถ้าคนรุมใช้เกิน 5 สาย มันจะตีหน้ามึนสวนกลับคืนเป็นข้อความ SSE error ปฏิเสธไปว่า "ระบบยุ่ง ขออภัย" ทันที ไม่ยอมปล่อยให้เซิร์ฟแฮงก์ (ตามกติกาใน [[03 - Runtime Views]])

## 2. `accident_chat.py` — โต๊ะกลมคุยเจาะลึกอุบัติเหตุ (prefix `/api/accident-chat`)

| วิธีเรียก (Method) | เส้นทางระบุ (Path)     | สิ่งที่ต้องป้อนมา (Request)         | รูปแบบผลลัพธ์ (Response)             | หมายเหตุ / ข้อควรระวัง                                                                         |
| ------------------ | ---------------------- | ----------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------- |
| POST               | `/ask`                 | ตัวพิมพ์ `AccidentChatRequest`      | ตอบมาเป็นร่าง `AccidentChatResponse` | ท่าไม้ตายแบบรุม 2-agent (ตัวนึงดำน้ำหา SQL→ ส่งต่ออีกตัว Answer ช่วยเกลาคำ)                    |
| POST               | `/ask/stream`          | ตัวพิมพ์ `AccidentChatRequest`      | **ทยอยยิง SSE**                      | หน้าตาเหมือนท่าแรกแต่แปลงเป็นเวอร์ชันสตรีมให้รออ่านสบายๆ                                       |
| POST               | `/quick`               | ตัวพิมพ์ `AccidentChatQuickRequest` | คืนค่าเป็นก้อน JSON ดิบๆ             | เน้นความไวแสง ดึงผ่าน SQL tools เลย **ไม่พึ่งพลังเวทมนตร์ LLM** เด็ดขาด (เหมาะสำหรับโชว์ตาราง) |
| GET                | `/provinces`           | —                                   | แค่รายชื่อจังหวัดของเขต 10           | เอาไว้ป้อนดรอปดาวน์                                                                            |
| GET                | `/districts?province=` | ส่งต้อยติ่งคำว่า `province` ต่อท้าย | ให้รายชื่อลิสต์อำเภอทั้งหมด          |                                                                                                |
| GET                | `/sample-questions`    | —                                   | ชุดตัวอย่างคำถามที่ควรถาม            | เอาไว้โชว์ให้ผู้ใช้เห็นว่าระบบเก่งด้านไหน                                                      |

**เจาะไส้ในของ `AccidentChatRequest`:** มีประโยคคำถาม `question: str` · ชี้เป้า `province: str` · ชี้เป้า `district: str` ·
ห้วงปี `year_start=2021` · ถึง `year_end=2026` (ระบบบังคับว่าปีนี้ต้องเป็น **ค.ศ.** เท่านั้น)
**เจาะไส้ในของ `AccidentChatQuickRequest`:** ระบุเครื่องมือ `tool: str` · พื้นที่ `province`/`district`/`road_name` · ระบุเจาะจงปี `year=2024` ·
หรือเป็นห้วง `year_start`/`year_end` · ขอเรียง `top_n=10` อันดับ · หรือจะเจาะเป้าหมาย `topic="helmet"` เรื่องหมวกกันน็อค
**ผลประกอบการ `AccidentChatResponse`:** จะพ่นคำตอบมาในซอง `answer` (สวยงามด้วยการตีแผ่เป็น Markdown) · พร้อมซองข้อมูลดิบ `raw_data` · แถมใบเตือนข้อจำกัด `data_limitations[]` · แผ่ลิสต์ท่าที่ใช้ `tools_used[]` · พร้อมใบบิลเวลาที่ผลาญไป `elapsed_seconds` · และเศษเหรียญ `metadata`

## 3. `accident_policy.py` — วงประชุมร่าง Policy Brief เจาะพื้นที่เขต 10 (prefix `/api/accident-policy`)

| วิธีเรียก (Method) | เส้นทางระบุ (Path) | สิ่งที่ต้องป้อนมา (Request) | รูปแบบผลลัพธ์ (Response) | หมายเหตุ / ข้อควรระวัง |
|---|---|---|---|---|
| GET | `/zone10/data` | — | ได้มาเป็น `Zone10DataResponse` | เป็นเส้นทางลัด ดึงตัวเลข SQL ดิบทะลวงตอบมา 7 หมวดคำถาม (**วิ่งโครตไว < 5 วิ**, ไม่ใช้ LLM) |
| POST | `/zone10` | โยนพิมพ์ `AccidentPolicyRequest` | งอกร่าง `AccidentPolicyResponse` | ท่าจัดเต็ม ปล่อย crew ลูกทีม 3 agent ช่วยกันถกเถียงและเรียบเรียงงาน (**กินเวลานาน 2–5 นาที**) |

**เจาะไส้ใน `AccidentPolicyRequest`:** หว่านมาเลยว่าเอากี่พื้นที่ `provinces: str[]` · ยิงกระสุนคำถาม `questions: str[]` · กินเวลาย้อนหลัง `year_range: int[]` · บังคับหน้าตา `format="markdown"`
**ผลประกอบการ `AccidentPolicyResponse`:** จะบอกพื้นที่เขตที่ทำ `zone` · รายชื่อ `provinces[]` · และม้วนคัมภีร์จัดเต็มนโยบาย `policy_brief` (แบบ Markdown) · ย่อยเป็นตอนๆ `sections` · จัดกราฟประกอบ `charts[]` · ยัดข้อมูลเสริม `metadata`

## 4. `obsidian.py` — ศูนย์รับเรื่องคลังสมององค์ความรู้ (prefix `/api/obsidian`)

| วิธีเรียก (Method) | เส้นทางระบุ (Path) | สิ่งที่ต้องป้อนมา (Request) | รูปแบบผลลัพธ์ (Response) | หมายเหตุ / ข้อควรระวัง |
|---|---|---|---|---|
| POST | `/search` | ใบสั่ง `ObsidianSearchRequest` | คืนกลับเป็น `ObsidianSearchResponse` | สั่งตะลุยค้นหาแบบถึกๆ ทนๆ ผ่านเครื่องมือ pg_trgm **ห้ามแตะต้อง LLM เด็ดขาด** |
| GET | `/notes` | แนบ query filters เล็กน้อย | คืนลิสต์รายการหน้าโน้ต | ใช้เช็คว่ามีอะไรบ้าง |
| GET | `/notes/{note_id:path}` | ยัด path ลงไป | คืนเนื้อในจดหมายโน้ตตัวนั้นมา | อ่านของจริง |
| POST | `/ask` | ส่งคำถามไปที่ `ObsidianAskRequest` | โต้ตอบมาที่ `ObsidianAskResponse` | สั่งให้ขุนคลังเข้าไปอ่านเต็มบริบทแล้วสรุปด้วย Gemini |
| POST | `/ask/stream` | ส่งไปที่เดิม `ObsidianAskRequest` | **ทยอยยิง SSE** | แบบเดียวกัน แต่ให้เป็นสตรีมค่อยๆ พิมพ์ |
| GET | `/status` | — | ตอบกลับด้วยหน้าต่าง `ObsidianStatusResponse` | ส่องดูว่าดัชนีเรียงของคลังไปถึงไหนแล้ว |
| GET | `/vaults` | — | ลิสต์รายการโกดัง vault ทั้งหมด | |
| POST | `/index` | ตัวสั่งงาน `ObsidianIndexRequest` | บันทึกความดีความชอบ `ObsidianIndexResult` | คำสั่งรื้อจัดระเบียบของ (re)index จาก vault ดันลงตาราง DB |
| POST | `/pdfs/sync` | — | ผลประกอบการ `ObsidianPdfSyncResult` | คำสั่งดูดอัปโหลดแผ่นเอกสาร PDF ถม → ลงโกดัง MinIO |
| POST | `/pdfs/sync-from-bucket` | — | ตอบกลับซื่อๆ ด้วย JSON | โหมดประหยัดแรง สั่งจับซิงก์จากถัง bucket ที่มีกะพี้ไว้อยู่แล้ว |
| GET | `/pdfs` | อาจใส่ข้อแม้ query | แจกแจงบัญชี `ObsidianPdfListResponse` | ดึงบัญชีรายการทรัพย์สิน PDF asset ทั้งหมด |
| GET | `/pdfs/note/{note_id:path}` | ระบุชื่อ path | ส่งม้วน PDF ประจำตัวของโน้ตนั้นมา | |
| GET | `/pdfs/pairs` | ข้อจำกัด query | คายทะเบียนคู่สมรส `ObsidianNotePdfPairsResponse` | โชว์ว่าใครคู่ใคร (คู่ note↔pdf) |

## 5. `thaijo.py` — สำนักงานสืบค้นหอสมุดงานวิจัย ThaiJo (tags: thaijo)

| วิธีเรียก (Method) | เส้นทางระบุ (Path) | สิ่งที่ต้องป้อนมา (Request) | รูปแบบผลลัพธ์ (Response) | หมายเหตุ / ข้อควรระวัง |
|---|---|---|---|---|
| POST | `/api/thaijo` | ยื่นจดหมาย `ThaiJoRequest` | **ทยอยยิงสตรีม SSE** | ลุยวิ่งผลัด Fetcher→ตามด้วย Planner→ปิดจ๊อบที่ Generator (แถมสตรีมผลงานมาในคราบ HTML) |
| POST | `/api/thaijo/report` | ยื่นจดหมายปั้นเรื่อง `ThaiJoGenerateRequest` | **ยิงเป็น SSE** | บิดงานวิจัยที่ควานหามาได้แล้ว ให้มาเป็นรูปเล่มรายงานทันที |

| 🆕 GET | `/ingest-batch/status/{batch_id}` | ถามความคืบหน้าทั้งคิว พร้อม **log เต็มรายไฟล์** |
| 🆕 POST | `/ingest-batch/cancel/{batch_id}` | ขอยกเลิกคิวที่ยังไม่ถึงคิวตัวเอง |

### 🆕 คิว ingest หลายไฟล์ (2026-07-30)

```json
// POST /pdf/ingest-batch
{ "items": [ { "file_id": "872002", "original_name": "นโยบาย.pdf" } ] }
// → { "batch_id": "38cc07eb-...", "total": 3, "status": "queued" }
```

`GET /ingest-batch/status/{id}` คืนรายไฟล์พร้อมสถานะ **6 แบบ**:
`pending` · `running` · `completed` · **`partial`** · `error` · `cancelled`

> [!warning] อย่าลืมสถานะ `partial`
> `partial` = ไฟล์ทำเสร็จแล้วแต่มีบางส่วนแปลงไม่ผ่าน (เช่น *"แปลงไม่สำเร็จ 1 จาก 14
> ส่วน: ส่วนที่ 4 (หน้า 61–80)"*) — ต้องแยกจาก `completed` ให้ชัด ไม่งั้นผู้ใช้เข้าใจว่า
> ได้ข้อมูลครบทั้งที่มีรูโหว่อยู่
>
> เคยพลาดมาแล้ว: type ฝั่ง frontend ประกาศไว้แค่ 5 สถานะ ตัวแปลข้อความจึงตกเข้า
> `default` แล้วโชว์ว่า **"รอคิว" ค้างตลอด** ทั้งที่ไฟล์ทำเสร็จไปแล้ว

ฟิลด์รายไฟล์ที่ส่งกลับ:

| ฟิลด์ | ความหมาย |
|---|---|
| `last_log` | บรรทัด log ล่าสุด (ใช้ตอนสถานะ `running`) |
| 🆕 `progress[]` | **log ทั้งก้อนของไฟล์นั้น** — เดิมส่งแค่ `last_log` ทำให้พอไฟล์เสร็จแล้ว log หายหมด เหลือแค่ "✅ เสร็จสิ้น" ตรวจสอบไม่ได้ว่าอ่านกี่หน้า แตกกี่ส่วน ส่วนไหนพัง |
| 🆕 `progress_truncated` | จำนวนบรรทัดที่ถูกตัดออก (เพดาน `_MAX_ITEM_LOGS = 120` บรรทัด/ไฟล์ — เอกสาร 400 หน้ายังไม่ถึงเพดาน) |
| `result` | สรุป `total_pages` / `total_chunks` / `saved_at` |

> 💡 จุดพักข้อมูล: พวกกอง endpoint ชุมทางกลุ่มนี้ ตัวพนักงานหน้าด่าน frontend จะไม่เรียกตรงๆ แต่จะเดินเข้ามาผ่านช่องทางสาย proxy ชื่อ `/api/pdf/*` เท่านั้น (ไปทบทวนเนื้อหาอ่านเพิ่มเติมได้ที่ [[07 - API Reference — Frontend (BFF)]])
