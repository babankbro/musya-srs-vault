# ⚖️ Agent Concurrency Manager — รองรับ 60–70 users พร้อมกัน

← [[01 - Backend Design]] · [[10 - Research Planner — ให้ Agent วางแผนค้นเอง]]

> **โจทย์:** ผู้ใช้มาก → จำกัด agent ต่อคนให้น้อย · ผู้ใช้น้อย → ให้ agent ต่อคนได้มาก
> และถ้าชนโควตา Gemini ให้หน่วง ไม่ใช่ปฏิเสธ

---

## 1. สภาพปัจจุบัน (ข้อเท็จจริงจากโค้ด)

```python
_AI_SEMAPHORE = threading.BoundedSemaphore(5)      # analyze.py:12
if not _AI_SEMAPHORE.acquire(blocking=False):      # analyze.py:1132
    yield "ระบบกำลังประมวลผลเต็มความสามารถ กรุณารอสักครู่แล้วลองใหม่"
```

| ปัญหา | ผล |
|---|---|
| เพดาน **5 request** ทั้งระบบ | 60 คนกดพร้อมกัน ⇒ **55 คนโดนเด้งทันที** |
| `blocking=False` = **ไม่มีคิว** | ผู้ใช้ต้องกดเองใหม่เรื่อย ๆ ไม่รู้ว่าต้องรอนานแค่ไหน |
| เลข 5 **ไม่ได้มาจากการวัด** | หาที่มาในโค้ด/เอกสารไม่เจอ |
| เพดานเดียวคุมทุกโหมด | แชทสั้น (2–3 LLM call) ถูกบล็อกโดยงานสร้างรายงาน (20–24 call) |
| ไม่มีการมองภาพรวม agent | 1 request ลาก agent ได้ถึง 24 ตัวโดยไม่มีใครนับ |

> [!note] Gemini ไม่ใช่คอขวด
> Tier 2 · Postpay รับได้มากกว่านี้มาก และ `error_logs/` **ยังไม่เคยมี 429 เลยสักครั้ง**
> เพราะเพดาน 5 กันไว้ก่อนอยู่แล้ว — **คอขวดคือโค้ดเรา**

## 2. หลักการออกแบบ

**แบ่งงบ agent รวมของทั้งระบบ ให้ผู้ใช้ที่กำลังใช้งานอยู่เท่า ๆ กัน**
ผู้ใช้มาก → ส่วนแบ่งน้อย · ผู้ใช้น้อย → ส่วนแบ่งมาก

```
งบต่อคน = clamp(  งบรวม ÷ จำนวนคนที่กำลังใช้งาน,  ขั้นต่ำ,  ขั้นสูง )
```

ตั้ง **งบรวม = 70 · ขั้นต่ำ = 1 · ขั้นสูง = 7** จะได้ตรงตามที่ต้องการพอดี:

| ผู้ใช้พร้อมกัน | 70 ÷ n | งบต่อคน | agent ทำงานจริงรวม |
|---:|---:|---:|---:|
| 5 | 14 | **7** (ชนเพดานบน) | 35 |
| **10** | 7 | **7** ✅ | 70 |
| 20 | 3.5 | **3** | 60 |
| 35 | 2 | **2** ✅ | 70 |
| **60** | 1.16 | **1** ✅ | 60 |
| 70 | 1 | **1** ✅ | 70 |
| 100 | 0.7 | **1** (ชนเพดานล่าง) | 70 + คิว |

**ขั้นต่ำ 1 สำคัญ** — ทุกคนต้องได้ทำงานเสมอ ไม่มีใครถูกอดตาย
เมื่อคนเกิน 70 จึงเข้าคิวแทนการลดต่ำกว่า 1

## 3. สถาปัตยกรรม 3 ชั้น

```
คำขอเข้ามา
   │
   ▼ ชั้น 1 — ประตูรับงาน (Admission)
   │   • เข้าคิวแทนการปฏิเสธ · บอกลำดับคิวและเวลาที่คาด
   │   • คิวเต็มจริง ๆ ค่อยปฏิเสธ พร้อมบอกเหตุผล
   ▼
   ▼ ชั้น 2 — งบ agent ต่อคน (AgentBudget)
   │   • คำนวณ clamp(งบรวม ÷ คนที่ใช้อยู่, 1, 7) ใหม่ทุกครั้งที่มีคนเข้า/ออก
   │   • pipeline ขอ slot ก่อน fan-out · ได้เท่าไรก็ยิงเท่านั้น ที่เหลือรอ
   ▼
   ▼ ชั้น 3 — แรงดันจาก Gemini (PressureController)
       • นับ 429 ในหน้าต่างเวลา → หดงบรวมชั่วคราว → ค่อย ๆ คืน
       • ต่อยอดจาก backoff+jitter ที่มีอยู่แล้วใน agent_defaults.py
```

### ชั้น 1 — เข้าคิว ไม่ใช่ปฏิเสธ

ส่ง event บอกสถานะระหว่างรอ ผู้ใช้จะได้ไม่กดซ้ำ (ซึ่งยิ่งซ้ำเติมโหลด)

```python
{"type": "queued", "position": 12, "eta_seconds": 240,
 "message": "คุณอยู่คิวที่ 12 · ประมาณ 4 นาที"}
```

> [!important] ปฏิเสธเมื่อไร
> ปฏิเสธเฉพาะตอน **คิวยาวเกินเวลาที่ยอมรับได้** (เช่น รอเกิน 10 นาที)
> และต้องบอกตรง ๆ ว่าเพราะอะไร ไม่ใช่ "ลองใหม่อีกครั้ง" ลอย ๆ

### ชั้น 2 — งบ agent ต่อคน

**นับ "คนที่กำลังใช้งาน" ไม่ใช่ "จำนวน request"** — คนเดียวเปิดหลายแท็บไม่ควรได้งบเพิ่ม

```python
class AgentBudget:
    TOTAL = 70          # งบ agent รวมทั้งระบบ
    MIN_PER_USER = 1
    MAX_PER_USER = 7

    def per_user(self) -> int:
        n = max(1, len(self._active_users))
        return max(self.MIN_PER_USER, min(self.MAX_PER_USER, self.TOTAL // n))

    def acquire(self, user_id: str, want: int, timeout: float) -> int:
        """ขอ slot — คืน "จำนวนที่ได้จริง" ซึ่งอาจน้อยกว่าที่ขอ"""
```

**จุดสำคัญ: `acquire` คืนจำนวนที่ได้จริง ไม่ใช่ True/False**
Research Planner วางแผน 7 ขั้น แต่ได้งบ 2 ⇒ **ยิง 2 ขั้นก่อน ที่เหลือทยอยตาม**
ไม่ใช่ล้มทั้งงานหรือยิงทั้ง 7 ฝ่าเพดาน

### ชั้น 3 — หดงบเมื่อ Gemini เริ่มบ่น

```
เจอ 429 → ลดงบรวมลง 30% (ต่ำสุดไม่ต่ำกว่า 20)
ไม่เจอ 429 ครบ 60 วิ → คืนงบ 10% จนกลับเท่าเดิม
```

**ลดเร็ว คืนช้า** — โควตาที่ตันแล้วต้องใช้เวลาฟื้น การรีบคืนงบจะไปตันซ้ำทันที

⚠️ **ต้องเก็บรายละเอียด 429 ที่ Google ส่งมาด้วย** (ชื่อโควตาและค่าเพดาน)
ตอนนี้โค้ด log แค่ว่าเจอแล้ว sleep กี่วินาที ⇒ **โดนครั้งแรกจะได้รู้เพดานจริงทันที**

## 4. แยกคิวตามน้ำหนักงาน

ปัญหาที่ต้องแก้พร้อมกัน: คนถาม *"ปี 2569 มีผู้ป่วยกี่คน"* ไม่ควรรอคนสร้างรายงาน

| ชั้นงาน | โหมด | LLM call | งบที่ขอ |
|---|---|---:|---:|
| **เบา** | แชทเปล่า · คลังรายงาน · เว็บ | 2–3 | 1 |
| **กลาง** | สถิติ · วิจัย | 6–8 | 2–3 |
| **หนัก** | แผน/นโยบาย | 20–24 | เท่าที่ได้ (สูงสุด 7) |

**กันงบส่วนหนึ่งไว้ให้งานเบาเสมอ** (เช่น 20% ของงบรวม) — ไม่งั้นงานหนักจะกินหมด
แล้วคำถามสั้น ๆ ที่ควรตอบใน 3 วินาทีต้องรอเป็นนาที

## 6. ตัวเลขที่ต้องวัดหลังใช้งาน

**ตั้งค่าเริ่มต้นเป็นการเดา ต้องปรับจากของจริง** — เลข 5 เดิมก็มาจากการเดาเหมือนกัน

- 429 ต่อชั่วโมง (ควรเป็น 0 ถ้างบตั้งถูก)
- เวลารอคิวเฉลี่ย / p95
- งบต่อคนที่คำนวณได้จริงตามช่วงเวลา
- จำนวนคนที่ถูกปฏิเสธเพราะคิวยาวเกิน

## 7. ความเสี่ยงที่รู้ตัว

> [!warning] ยังไม่มีใครวัดว่าเครื่องรับไหวแค่ไหน
> ขยายจาก 5 → 70 agent อาจไปชน **ขีดจำกัดของเครื่อง** แทน (RAM/CPU)
> โดยเฉพาะ Python Executor ที่ spawn subprocess ทุกครั้ง
> **ต้องทดสอบโหลดจริงก่อนตั้ง TOTAL = 70** ไม่ใช่เชื่อตัวเลขนี้เลย

> [!warning] งบเป็นของ process เดียว
> ถ้าขยายเป็นหลาย container ต้องย้ายตัวนับไป **Redis** (มีอยู่แล้วในระบบ
> แต่ตอนนี้ใช้แค่ cache ของ ThaiJo) ไม่งั้นแต่ละ container จะนับแยกกัน
> แล้วงบรวมจริงกลายเป็น 70 × จำนวน container

> [!warning] "จำนวนคนที่กำลังใช้งาน" นิยามไม่ตรงไปตรงมา
> ต้องมี timeout ล้างคนที่ปิดแท็บทิ้งไว้ ไม่งั้นงบต่อคนจะหดลงเรื่อย ๆ
> จากผู้ใช้ที่ไม่ได้อยู่จริง
