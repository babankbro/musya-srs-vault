# 🧭 Research Planner — ให้ Agent วางแผนค้นข้อมูลเอง

← [[01 - Backend Design]] · [[06 - Report Generation Workflow]] · [[07 - ผลทดสอบจริง 8 ข้อ (Baseline Run 1)]]

> **ปัญหา:** ปุ่ม "แผนหรือนโยบาย" ยิงคำถาม **ก้อนเดียวกันเป๊ะ** ใส่ทั้ง 5 แหล่งพร้อมกัน
> **เป้าหมาย:** ให้ Agent อ่านโจทย์ → วางแผนเอง → เลือกเครื่องมือเอง → ตั้งคำค้นเอง
> เรียกเครื่องมือเดิมซ้ำได้หลายครั้งถ้าจำเป็น

---

## 1. ปัญหาที่ต้องแก้ (ยืนยันจากโค้ดจริง)

`analyze.py` โหมด `report-gather` เรียกทุก worker ด้วยตัวแปรเดียวกัน:

```python
run_thaijo_pipeline(prompt=prompt, ...)
run_pubmed_pipeline(prompt=prompt, ...)   # ← ประโยคไทยเข้า PubMed
_worker_tavily(prompt=prompt, ...)
```

ส่ง *"จัดทำแผนปฏิบัติงาน 1 ปี ลดอุบัติเหตุรถจักรยานยนต์กลุ่มอายุ 15–24 ปี จ.อุบลราชธานี"*
เข้า **PubMed** ตรง ๆ — เป็น **คำสั่งสร้างเอกสาร ไม่ใช่คำค้นงานวิจัย** และเป็นภาษาไทย

> [!danger] คำสั่งสร้างเอกสาร ≠ คำค้นข้อมูล
> โจทย์เดียวต้องการหลักฐานคนละชนิดสำหรับแต่ละหัวข้อของแผน
> การยิงประโยคเดียวใส่ทุกแหล่งจึงได้ผลดีเฉพาะแหล่งที่บังเอิญเข้ากับรูปประโยคนั้น

**ข้อจำกัดอื่นของ flow ปัจจุบัน:**

| ข้อจำกัด | ผล |
|---|---|
| เรียกแต่ละแหล่งได้ **ครั้งเดียว** | ถามสถิติได้คำถามเดียว ทั้งที่แผนต้องการตัวเลข 4–5 ชุด |
| ลำดับตายตัว ยิงพร้อมกันหมด | ใช้ผลรอบแรกมาตั้งคำค้นรอบสองไม่ได้ |
| ไม่บังคับค้นบริบทพื้นที่ | บางครั้งได้แผนที่ไม่อ้างเอกสารของเขตเลย |

## 2. สิ่งที่จะสร้าง

### Research Planner Agent

รับโจทย์ → คืน **แผนค้นข้อมูลเป็น JSON** ก่อนเริ่มค้นจริง

```json
[
  {"tool": "obsidian", "query": "รายงานตรวจราชการ อุบลราชธานี ความปลอดภัยทางถนน",
   "purpose": "บริบทพื้นที่"},
  {"tool": "obsidian", "query": "นโยบายความปลอดภัยทางถนน เขตสุขภาพที่ 10 ระดับประเทศ",
   "purpose": "นโยบายเขต/ประเทศ"},
  {"tool": "stats", "query": "อุบัติเหตุทางถนนในอุบลราชธานี ปี 2564-2569 แยกรายปี",
   "purpose": "ตัวเลขฐาน"},
  {"tool": "stats", "query": "ถนนสายไหนในอุบลราชธานีมีอุบัติเหตุสูงสุด 10 อันดับ",
   "purpose": "จุดเสี่ยง"},
  {"tool": "pubmed", "query": "motorcycle helmet intervention adolescent Thailand",
   "purpose": "หลักฐานมาตรการ"}
]
```

**ความสามารถที่เพิ่มขึ้น:**
- เลือกเครื่องมือเองตามความเหมาะสม ไม่ต้องใช้ครบทุกตัว
- **เรียกเครื่องมือเดิมซ้ำได้หลายครั้ง** ด้วยคำค้นต่างกัน
- ตั้งคำค้นให้เหมาะกับแต่ละแหล่ง (ไทยสำหรับ ThaiJo/คลัง · อังกฤษ MeSH สำหรับ PubMed)
- ระบุ `purpose` ทำให้จัดกลุ่มผลลัพธ์ตาม "หัวข้อของแผน" แทนที่จะตาม "ชื่อเครื่องมือ"

### 🔒 กฎบังคับ — ต้องค้นคลังรายงานทุกครั้ง

> [!important] ทุกแผนต้องมี `obsidian` อย่างน้อย 2 รายการเสมอ
> 1. **บริบทพื้นที่** — จังหวัด/อำเภอที่โจทย์ระบุ
> 2. **นโยบายเขต/ประเทศ** — ทิศทางระดับเขตสุขภาพที่ 10 และระดับชาติ
>
> **เหตุผล:** แผนปฏิบัติงานราชการต้องสอดคล้องกับสิ่งที่พื้นที่ทำอยู่จริงและนโยบายต้นสังกัด
> ถ้าเสนอมาตรการที่ขัดกับแผนเขต หรือซ้ำกับสิ่งที่ทำไปแล้ว **แผนนั้นใช้ไม่ได้**
> ต่อให้เนื้อหาดีแค่ไหน
>
> บังคับด้วย **โค้ด** ไม่ใช่แค่พรอมต์ — ถ้า planner ไม่ใส่มา ระบบเติมให้เอง

## 3. สถาปัตยกรรมใหม่

```
โจทย์
  ▼
🧭 Research Planner ── วางแผน 4–8 ขั้น (JSON)
  ▼
🔒 normalize_plan() ── การ์ดเชิงโค้ด:
     • เติม obsidian บริบทพื้นที่ + นโยบาย ถ้าขาด
     • ตัดขั้นเกินลิมิต · ตัดเครื่องมือที่ไม่รู้จัก
     • กันคำค้นว่าง/ยาวเกิน
  ▼
⚙️ รันตามแผน (ThreadPool ทยอย 1.5 วิ เหมือนเดิม)
     ตัวไหนพังไม่ล้มทั้งชุด
  ▼
📄 รวมผลจัดกลุ่มตาม `purpose` ไม่ใช่ตามชื่อเครื่องมือ
```

**สิ่งที่ไม่เปลี่ยน** — worker ทั้ง 5 ตัวเดิม · การทยอยยิง 1.5 วิ กัน 429 ·
`report_source_status` events · ปุ่มลองใหม่ · Guard จังหวัดนอกเขต 10

## 4. การ์ดที่ต้องมี (บทเรียนจากงานรอบก่อน)

| การ์ด | ทำไม |
|---|---|
| จำกัด **4–8 ขั้น** | ป้องกัน planner สั่งค้น 30 รอบจนช้าและเปลือง quota |
| **เครื่องมือต้องอยู่ในรายการที่รู้จัก** | กันแต่งชื่อเครื่องมือขึ้นเอง (เคยแต่งชื่อชุดข้อมูลมาแล้ว) |
| **บังคับ obsidian ≥ 2** | ตามกฎข้างบน |
| **planner ล้ม → ถอยไปใช้แผนเดิม 5 แหล่ง** | ห้ามทำให้ฟีเจอร์ที่ใช้ได้อยู่แล้วพัง |
| **คำค้นยาวไม่เกิน ~200 ตัว** | คำค้นยาวเกินคือสัญญาณว่า planner คัดลอกโจทย์มาทั้งก้อน |

> [!warning] ห้ามเชื่อ JSON จาก LLM ตรง ๆ
> ทุกฟิลด์ต้องผ่าน `normalize_plan()` ก่อนใช้ · ตลอดงานรอบนี้พบว่า LLM
> **แต่งชื่อชุดข้อมูล** และ **หยิบคอลัมน์ผิด** มาแล้ว — สมมติฐานว่า "โมเดลทำตามที่สั่ง"
> พิสูจน์แล้วว่าเชื่อไม่ได้

**ตัวชี้วัดความสำเร็จ:** โจทย์ *"แผน 1 ปี ลดอุบัติเหตุรถจักรยานยนต์ 15–24 ปี อุบลฯ"*
ต้องได้แผนที่ค้นสถิติ ≥ 2 คำถาม · คลังรายงาน ≥ 2 · PubMed เป็นภาษาอังกฤษ

# ✅ ผลจริง (2026-08-03)

## แผนที่ Agent สร้างเองสำหรับโจทย์จริง

```
1. [obsidian] บริบทพื้นที่      → อุบัติเหตุรถจักรยานยนต์ อุบลราชธานี 15-24 ปี
2. [stats   ] ข้อมูลเชิงปริมาณ  → สถิติอุบัติเหตุรถจักรยานยนต์ อุบลราชธานี ปี 2565-2566
3. [thaijo  ] งานวิจัยไทย       → ปัจจัยเสี่ยง อุบัติเหตุ จักรยานยนต์ วัยรุ่น
4. [pubmed  ] งานวิจัยสากล      → motorcycle accidents young adults risk factors prevention
5. [obsidian] นโยบายเขต         → นโยบายความปลอดภัยทางถนน เขตสุขภาพที่ 10
6. [tavily  ] มาตรการล่าสุด     → มาตรการลดอุบัติเหตุรถจักรยานยนต์ เยาวชน 2567
7. [stats   ] ผลการดำเนินงาน    → ผลโครงการลดอุบัติเหตุฯ อุบลราชธานี
```

**ผ่านตัวชี้วัดครบ** — `stats`×2 · `obsidian`×2 · PubMed เป็นอังกฤษ · คำค้นต่างกันทุกขั้น

## แสดงวิธีคิดเห็นแผนและคำค้นแล้ว

เพิ่ม agent step **"Research Planner"** ที่พิมพ์แผนทั้งหมดพร้อมคำค้นรายขั้นออกมา
⇒ ตรวจย้อนกลับได้ว่าระบบเอาคำอะไรไปค้นที่ไหน ซึ่งเดิมมองไม่เห็นเลย

# 🐛 บั๊กที่ตามมาทันที — และวิธีแก้

## 1. รายงาน PDF/Word เนื้อหาหายไป (ผู้ใช้จับได้)

ตัวเก็บผลลัพธ์เป็น **dict เดียวต่อเครื่องมือ**:

```python
stats_final_holder["msg"] = ev.get("message", "")   # เขียนทับทุกครั้ง
obsidian_result["content"] = obs.content            # เขียนทับทุกครั้ง
```

พอ planner เรียกเครื่องมือเดิมซ้ำ **ผลรอบแรกถูกเขียนทับหายเงียบ ๆ**
⇒ รายงานเหลือเนื้อหาจากการค้นรอบสุดท้ายเท่านั้น (ได้ "นโยบายเขต" แต่ไม่มี "บริบทพื้นที่")
และถ้ารันพร้อมกันก็ยัง **แย่งเขียน dict เดียวกัน** ผลปนกันแบบเดาไม่ได้

> [!danger] บทเรียน: ฟีเจอร์ใหม่ทำลายฟีเจอร์เก่าโดยไม่มีอะไรฟ้อง
> `journal-template` ไม่ได้ถูกแก้เลยตั้งแต่ 24 มิ.ย. — ปัญหาอยู่ที่**เนื้อหาที่ป้อนเข้า**
> ไม่ใช่ตัว template · ถ้าไม่มีผู้ใช้รายงาน คงไม่มีใครสังเกต

**แก้ 2 ชั้น:**
1. จับขั้นของเครื่องมือเดียวกันเป็น **"สายโซ่" รันเรียงกัน** (ต่างเครื่องมือยังขนานเหมือนเดิม)
2. ดูดผลของขั้นก่อน ๆ เก็บใน `_extra` แล้ว **ต่อกลับตอนประกอบ section** พร้อมติดป้ายว่า
   ส่วนไหนมาจากคำค้นอะไร

**โครงสร้าง section เหมือนเดิมทุกอย่าง** ⇒ PDF/Word กลับมาเหมือนเวอร์ชันก่อนหน้า
เทสต์ล็อกไว้ว่า **เรียกครั้งเดียวต้องได้ผลเท่าเดิมเป๊ะ ไม่มีป้ายกำกับงอกเพิ่ม**

## 2. ผลค้น ThaiJo ไม่ตรงหัวข้อ (ผู้ใช้จับได้)

**บั๊กนี้มีมาก่อนงานรอบนี้ทั้งหมด** — Planner แค่ทำให้เห็นชัดขึ้นเพราะคำค้นเจาะจงกว่าเดิม

วัดกับ API จริง — `strict=false` **คืน 10,000 ผลทุกคำค้น** (ชนเพดาน = แทบไม่กรองเลย):

| คำค้น | `strict=true` | `strict=false` |
|---|---:|---:|
| ปัจจัยเสี่ยง อุบัติเหตุ จักรยานยนต์ วัยรุ่น | **8** | 10,000 |
| อุบัติเหตุจักรยานยนต์ วัยรุ่น | **18** | 10,000 |
| ซึมเศร้า ผู้สูงอายุ | **845** | 10,000 |

**ต้นตอ:** พรอมต์ Keyword Extractor เขียนตัวอย่าง JSON ไว้ว่า `"strict": false`
โมเดลจึงลอกตามแทบทุกครั้ง — ทั้งที่ค่า fallback ในโค้ดใช้ `strict: True` อยู่แล้ว
⇒ **ทางที่ทำงานปกติกลับแย่กว่าทางสำรอง**

**แก้ 3 ชั้น:** แก้พรอมต์ · **บังคับ `strict=True` ในโค้ด** (ไม่พึ่งพรอมต์) ·
บันไดถอย `strict เต็มคำ → strict ตัดเหลือ 2 คำ → loose (ทางสุดท้าย)`

ผลหลังแก้ ด้วยคำค้นเดิมเป๊ะ — **ตรงหัวข้อทั้ง 5 บทความ**:
*ปัจจัยที่มีผลต่อพฤติกรรมเมาแล้วขับของผู้ขับขี่รถจักรยานยนต์* ·
*ปัจจัยทำนายพฤติกรรมความปลอดภัยในการขับขี่* ·
*การประยุกต์ใช้ Swiss Cheese Model กับการป้องกันอุบัติเหตุ*

## 3. ผลค้นไม่ตรงเพราะถูกเติมชื่อจังหวัด

โผล่ตามมาอีก 2 ครั้ง (ThaiJo และ PubMed) แยกบันทึกไว้ที่
[[11 - บั๊กตระกูล เติมพื้นที่ที่ผู้ใช้ไม่ได้ถาม]] เพราะเป็นตระกูลเดียวกับ
การย่อขอบเขตที่แก้ไปตอนต้น ไม่ใช่บั๊กเดี่ยว

## 4. ลิงก์อ้างอิงยาวจนกลืนทั้งหน้า

URL ภาษาไทยถูกเข้ารหัสเป็น percent-encoding ยาว **300+ ตัวอักษรต่อรายการ**
รายการอ้างอิง 8 รายการจึงกินพื้นที่ทั้งหน้ารายงาน

ต้นตอ: `_linkify_bare_urls` ใช้ **URL เต็มเป็นข้อความลิงก์**

แก้ด้วย `src/tools/link_text.py` — ถอดรหัสกลับเป็นไทยแล้วย่อ โดย **`href` ยังเป็น URL เต็ม**

```
scribd.com/document/852131003/%E0%B8%A3%E0%B8%B2%E0%B8%A2...  (300+ ตัว)
        ↓
scribd.com/852131003/รายงานประจำปีกรมสุขภาพจิต
```

หลักการ: เก็บ **2 ส่วนท้ายของ path** (ชื่อเอกสารจริงอยู่ตรงนั้น ส่วนต้นมักเป็นเลขระบบ) ·
ตัดตรงกลางแต่ **เก็บนามสกุลไฟล์ไว้** เพราะบอกชนิดเอกสาร ·
ไม่แตะลิงก์ที่มีข้อความอยู่แล้วและ URL ที่สั้นพอ

## 5. ปุ่มนำข้อมูลเดิมไปทำเอกสารอีกฉบับ

```
[ข้อมูลพื้นฐาน]  ใช้ข้อมูลนี้ทำต่อ:  [📋 นโยบาย] [📜 ยุทธศาสตร์] [📅 แผนปฏิบัติงาน]
```

**เหตุผล:** ข้อมูลชุดเดียวใช้ทำได้ทั้งสามแบบ — ต่างกันที่ **วิธีเรียบเรียง ไม่ใช่ที่ข้อมูล**
และการค้นคือขั้นที่กินเวลาและ quota มากที่สุด (7 ขั้น หลายนาที) ⇒ ข้ามไปหน้าเลือกหัวข้อเลย

โครงสร้างมีอยู่แล้ว — `ReportGatherData.combinedText` ถูกบันทึกลง DB ต่อข้อความอยู่ก่อนแล้ว
งานจึงเป็นการต่อสายเป็นหลัก: LeftPane เติมข้อมูล**ของข้อความนั้น ๆ** กลับเข้า store
(ผู้ใช้อาจกดจากข้อความเก่า ไม่ใช่ชุดล่าสุด) แล้วยิง event `reuse-report-base` ให้ RightPane

⚠️ ต้องหน่วง 1 macrotask ก่อนสั่งเลือกประเภทเอกสาร ไม่งั้นเลือกตอน base ยังว่าง —
ปัญหาลำดับ mount แบบเดียวกับที่โค้ดเดิมเคยเจอและมีคอมเมนต์เตือนไว้แล้ว

## ยังไม่จบ

- **ปุ่มใช้ข้อมูลซ้ำยังไม่ได้ทดสอบในเบราว์เซอร์** — หน้าเว็บต้องล็อกอิน
  ยืนยันได้แค่ type-check ผ่าน · ตัวแปรอยู่ในขอบเขต · ลำดับประกาศถูกต้อง
- **ยังไม่ได้รัน report-gather เต็มรูปแบบจากหน้าเว็บ** — ทดสอบแยกเป็นส่วน ๆ เท่านั้น
- **ป้ายสถานะซ้ำ** — ถ้าแผนมี `stats` 2 ขั้น หน้าเว็บเห็นป้ายเดียวอัปเดตทับกัน
  ต้องแก้ฝั่ง frontend ให้ key ด้วย index
- **ยังไม่ได้ตรวจ PubMed** ว่ามีปัญหา strict คล้าย ThaiJo หรือไม่
