# 🧠 ข้อมูลอ้างอิง: กลยุทธ์พรอมต์และการป้องกันข้อมูลมั่ว (Prompt Strategy & Anti-Hallucination)

← กลับไป [[01 - SSE Event Protocol]] · ตอนถัดไป → [[03 - Traceability Matrix]] · แวะดูแคตตาล็อกเอเจนต์: [[00 - Agent Catalogue]]

> โน้ตฉบับนี้อธิบายถึง **"หลักคิดร่วม (Design Philosophy) / หรือเหตุผลว่าทำไมถึงต้องร่ายเวทมนตร์พรอมต์แบบนี้"** ที่แฝงอยู่เบื้องหลังเงาของเอเจนต์ทุกตัวในระบบ —
> เหตุผลง่ายๆ คือ ความน่าเชื่อถือของคำตอบ (Trust) เป็นเรื่องคอขาดบาดตายสำหรับระบบผู้บริหาร นี่คือหัวใจสำคัญในการต่อยอดไปสู่เป้าหมายของระบบในเฟส 2

## 1. หลักการใหญ่อันดับหนึ่ง: การหย่าร้างระหว่าง "กระบวนการคิด" ออกจาก "การคิดเลข"

เราวางข้อกำหนดเด็ดขาดว่า **ระบบจะไม่ยอมให้ LLM นั่งเทียนคิดเลขเองโดยเด็ดขาด** — โมเดล AI มีหน้าที่แค่ *ตีความหมาย/ เลือกวิธีแก้ปัญหา/ เขียนสคริปต์โค้ด/ และนำผลมาเรียบเรียงภาษา* ส่วนตัวเลขจริงที่จะตอบ ต้องดึงมาจากการรันโค้ด หรือ SQL บนฐานข้อมูลจริงเท่านั้น:

| เนื้องาน | ใครเป็นคนทำ | เหตุผล (ทำไมถึงให้คนนี้ทำ) |
|---|---|---|
| เลือกไฟล์/โฟลเดอร์ที่เกี่ยวข้อง | **LLM** (ใช้กึ๋นเข้าใจความหมาย) | เพราะ AI เก่งเรื่องการตีความหมายภาษาไทยที่ดิ้นได้ |
| แปลงชื่อโฟลเดอร์ → ชี้เป้า file ID จริง | **โค้ดไพธอน** (`_resolve_folders_to_files` คู่กับตาราง `path_index`) | เพราะต้องเป๊ะแบบ 100% ห้ามสะกดผิดแม้แต่ตัวเดียว |
| คำนวณสถิติ บวกลบคูณหาร | **โค้ดไพธอน** (`execute_python_code` ในกรง subprocess) | เพราะตัวเลขสถิติต้องถูกต้องแม่นยำ และต้องตรวจสอบย้อนกลับ (Audit) ได้ |
| เรียบเรียงร่างรายงานเขียนตอบ | **LLM** (โดยมีข้อแม้ว่า ต้องลอกมาจาก Execution Result เท่านั้น) | เพราะ AI เก่งเรื่องการสละสลวยภาษาทางการ |

> **บทสวดคาถาหลัก:** *"ให้ AI เลือกความหมาย · แต่ให้โค้ดเป็นตัวชี้เป้าความจริง (resolve ตัวตน)"* (อ่านเพิ่มเติมการทำงานนี้ได้ที่ [[02 - Stats Tool Agents]])

## 2. แกนกลางกฎเหล็ก (Core Policy) ที่ถูกฉีดเข้าเส้นเลือดเอเจนต์ (`prompt_profile.py`)

พรอมต์ของทีมเอเจนต์วิเคราะห์ จะไม่ได้เกิดจากการเขียนร่ายยาวมั่วๆ แต่จะถูกประกอบร่างแบบเลโก้ผ่านฟังก์ชัน `join_prompt(expertise, role_prompt, CORE_POLICY)`:

| ชิ้นส่วนพรอมต์ (ค่าคงที่) | บทบาทและหน้าที่กำกับ |
|---|---|
| `ANALYST_CORE_POLICY` | กติกาการเขียนรายงาน — บังคับให้ใช้เฉพาะข้อมูลที่ได้มาจริง, หากประเมินต้องระบุชัดว่าเป็นค่าประมาณ, และห้ามปั้นตัวเลขหลอกขึ้นเองเด็ดขาด |
| `CODE_GENERATOR_CORE_POLICY` | กติกาการปั้นโค้ด — บังคับว่าผลลัพธ์โค้ด (output) ต้องมีป้าย label และชื่อตัวแปรที่คนอ่านรู้เรื่อง และโค้ดต้องกดรันแล้วผ่านทันที |
| `INSIGHT_RESPONSE_BLUEPRINT` | โครงร่างแบบแปลนคำตอบเชิงวิเคราะห์ (บังคับเขียน LaTeX formula สำหรับอธิบายสูตรวิธีคำนวณ) |
| 🆕 `NUMBER_FORMAT_POLICY` | กติกาการแสดงตัวเลข **แยกตามชนิดตัวเลข** — ตัวนับ (คน/ราย/ครั้ง) ต้องเป็นจำนวนเต็มพร้อมคั่นหลักพัน · อัตราส่วน (ร้อยละ/อัตรา/ค่าเฉลี่ย) แสดง 2 ทศนิยม |
| `MISSING_DATA_POLICY` | คู่มือวิธีรับมือเมื่อหาข้อมูลไม่เจอ — สั่งให้แจ้งเตือนผู้ใช้ตรงๆ ห้ามแอบเนียนเดาสุ่มข้อมูลเอาเอง |
| ฟังก์ชัน `join_prompt()` | กาวเชื่อมประสาน เอาความเป็นผู้เชี่ยวชาญ + บทบาทตัวละคร + กฎเหล็ก policy มารวมร่างเป็นพรอมต์เดียว |

## 3. สารพัดกลไกดักตีหัวกันข้อมูลมั่ว (Anti-Hallucination Mechanisms)

| ชื่อกลไก | ซ่อนอยู่ที่ไหน | ผลลัพธ์ที่ได้ |
|---|---|---|
| **"จงใช้เฉพาะผลจาก Execution Result"** | ฝังใน backstory ของเอเจนต์ตัวเขียนรายงานทุกตัว | บล็อกไม่ให้ AI เผลออ้างตัวเลขแปลกๆ ที่ไม่ได้หลุดมาจากการรันโค้ดจริง |
| **"ห้ามปั้นแต่งตัวเลขขึ้นเอง"** | พรอมต์ของทีม Answer/Report Writer | คาถาป้องกันการมั่วแต่งเรื่อง (anti-fabrication) |
| **บังคับแปะเชิงอรรถข้อจำกัดข้อมูล** | ทีมขุดอุบัติเหตุ Accident SQL tools | บังคับประจานตัวเองให้ผู้ใช้รู้ เมื่อข้อมูลตารางบางช่องมันโบ๋ (เช่น `fact_accident_person` ไม่มีบันทึกพฤติกรรม) |
| **บังคับแปะป้าย "ค่าประมาณจาก X"** | เอเจนต์ Insight Analyst | เพิ่มความโปร่งใสขั้นสุดเมื่อจำเป็นต้องใช้เทคนิคสุ่มเดาตัวเลข (Estimate) |
| **(Obsidian) ตอบเฉพาะเรื่องที่มีในเอกสารเท่านั้น** | ล็อกสเปคใน `obsidian_fullcontext` SYSTEM_PROMPT | ถ้าหาเอกสารอ้างอิงไม่เจอ → ให้ตอบเสียงแข็งไปเลยว่า "ไม่พบข้อมูลในคลังความรู้" |
| **`dedupe_repeated_answer`** | ท่อฝั่ง obsidian | กลไกดักตีหัว AI ที่ชอบพูดจาซ้ำซากวนลูป |
| **การ์ดด่านหน้า (out-of-zone guard) + `missing_data_logger`** | ไฟล์หน้าประตู `analyze.py` | ถามชื่อจังหวัดนอกเขต 10 → ยามจะถีบส่งแล้วแจ้งทันทีว่าไม่มีข้อมูล (สอดคล้องกับ [[03 - Functional Requirements|FR-CHAT-08]]) |
| **ระบบแปลงสลับ พ.ศ.↔ค.ศ.** | ท่อฝั่ง accident และ obsidian | ล้างบางปัญหา AI ค้นหาปีผิด (สอดคล้องกับ [[03 - Functional Requirements|FR-CHAT-09]]) |
| **แปะป้ายอ้างอิง (citation) แบบแยกแหล่ง** | ท่อสาย research และ report | บังคับการอ้างอิงต้องชี้เป้าตามแหล่งข้อมูลชัดเจน ไม่ใช่ปั้นยำรวมเป็นก้อนเดียว (สอดคล้องกับ [[03 - Functional Requirements|FR-REPORT-08]]) |
| 🆕 **Anti-leak guard 3 ชั้น (กันเนื้อหาดิบต้นฉบับหลุด)** | `obsidian_fullcontext.py` | ดูหัวข้อ 3.1 ด้านล่าง — กันบล็อก `FILE:` / YAML frontmatter / wikilink `[[...]]` หลุดเข้าคำตอบที่ผู้ใช้เห็น |
| 🆕 **Follow-up แบบบล็อก JSON (`<<<FOLLOWUPS>>>`)** | `obsidian_fullcontext.py` | เลิกใช้ regex เดาว่า "รายการเลขข้อ" ในคำตอบคืออะไร — เดิมมันไปหยิบหัวข้อ markdown ของคำตอบเอง (เช่น `1. **สรุปคำตอบ**`) มาโชว์เป็นปุ่มคำถามแนะนำผิด ๆ |
| 🆕 **บังคับห่อ URL เป็นลิงก์ (`_linkify_bare_urls`)** | `thaijo_agent.py` | พรอมต์สั่งให้ห่อ `<a href>` แล้วแต่ LLM ทำบ้างไม่ทำบ้าง (non-deterministic) จึง post-process ห่อให้เองทีหลังเสมอ ไม่พึ่งพรอมต์อย่างเดียว |
| 🆕 **แปลง path สัมพัทธ์เป็น URL เต็มก่อนป้อน LLM** | `analyze.py` + `PUBLIC_APP_URL` | LLM ไม่ยอมทำ `/api/pdf/view/123` เป็นลิงก์คลิกได้ (ต่างจาก `https://...` ของ ThaiJo/PubMed) จึงต้องเติมโดเมนให้ครบก่อนฝังลงข้อความ |
| 🆕 **Relevance gate รายไฟล์ (per-file) ผูก Redis** | `csv_pipeline.py` + `history.py` | เดิมข้าม gate ทั้งดุ้นเมื่อ "มี history" ทำให้คำถามที่ 2 เป็นต้นไปหยิบไฟล์คนละโดเมนได้โดยไม่มีด่านจับ — ตอนนี้ข้ามเฉพาะ `file_id` ที่เคยผ่าน gate มาแล้วในเซสชันนั้นจริง ๆ |
| 🆕 **Relevance Filter ของผลค้นงานวิจัย** | `research_relevance.py` (ThaiJo + PubMed) | ฐานข้อมูลวิจัยจับคู่ด้วย **คำ** ไม่ใช่ **ความหมาย** — ถาม "มาตรการลดหวานมันเค็ม" แล้วได้ *"การรุกล้ำความเค็มในแม่น้ำท่าจีน"* ปนมา จึงต้องมีด่านอ่านความหมาย **หลัง** ได้ผลค้นแล้ว (ดู [[04 - Research Tool Agents]] A0.5) |
| 🆕 **กันจำนวนคนมีทศนิยม 2 ชั้น** | `prompt_profile.NUMBER_FORMAT_POLICY` (ต้นทาง) + `chartAdvisor.formatCell()` (ปลายทาง) | เดิมสั่ง `df_display.round(2)` ทั้ง DataFrame ⇒ *"ผู้ป่วยเบาหวานขึ้นทะเบียน 45,231.00 คน"* หลุดเป็นคำตอบจริง · พรอมต์คือ "ขอความร่วมมือ" ไม่ใช่การบังคับ จึงต้องมีชั้นจัดรูปตอนแสดงผลด้วย (ดู [[02 - Frontend Design]] §5.5) |

### 3.1 🆕 เจาะลึก Anti-leak guard — กันเนื้อหาดิบของเอกสารต้นฉบับหลุดเข้าคำตอบ

> [!bug] บั๊กจริงที่เคยเจอ
> คำถามกว้าง ๆ อย่าง **"มีเอกสารอะไรบ้าง"** ทำให้ Gemini คัดลอกบล็อก `## FILE: ...` พร้อม YAML frontmatter และ wikilink ทั้งดุ้นมาแปะเป็นคำตอบ — ผู้ใช้เห็นไส้ในของระบบ ingest เต็ม ๆ

ระบบวางด่านไว้ **3 ชั้นซ้อนกัน** (ทุกชั้นมีเทสต์คุมใน `tests/test_obsidian_fullcontext.py`):

| ชั้น | กลไก | ทำงานเมื่อไร |
|---|---|---|
| **1. พรอมต์** | `SYSTEM_PROMPT` มีหัวข้อ **"ห้ามเด็ดขาด (anti-leak)"** สั่งห้ามคัดลอก `FILE:` / YAML / wikilink / เลขหน้าดิบ — ให้เรียบเรียงใหม่ด้วยคำพูดตัวเองเสมอ | ก่อนเริ่มตอบ |
| **2. เบรกมือระหว่างสตรีม** | เฝ้าดู **หาง 400 ตัวอักษร** ของบัฟเฟอร์ทุกครั้งที่โตขึ้น ถ้าจับร่องรอยได้ → **หยุดยิง `obsidian_chunk` ทันทีกลางคัน** (แต่ยังสะสมข้อความในหน่วยความจำต่อจนจบ เพื่อส่งต่อให้ชั้น 3) | ระหว่าง Gemini กำลังเขียน |
| **3. guard + retry + ตัดทิ้ง** | จบสตรีมแล้วตรวจทั้งก้อนอีกรอบ ถ้ายังเจอ → **เรียก Gemini ใหม่ด้วยพรอมต์ที่เข้มขึ้น** (`_LEAK_RETRY_SUFFIX`) ถ้า retry แล้ว*ยัง*หลุดอีก → `_strip_leaked_blocks()` ตัดบล็อกออกเองแบบ best-effort | หลังได้คำตอบเต็ม |

ตัวจับใช้ regex 4 ตัว: `_FILE_MARKER_RE` (บรรทัด `FILE:`), `_YAML_BLOCK_RE` (บล็อกคั่นด้วย `---`), `_YAML_FENCE_RE` (` ```yaml `), `_WIKILINK_RE` (`[[...]]`)

> [!important] ผลกระทบต่อฝั่งหน้าจอ
> เพราะชั้นที่ 2 อาจ **ตัดสตรีมจบกลางประโยคโดยตั้งใจ** ฝั่ง frontend จึง**ห้ามเอาผลรวมของ `obsidian_chunk` ไปใช้เป็นคำตอบสุดท้ายเด็ดขาด** — ต้องรอ event `result` เสมอ (ดู [[01 - SSE Event Protocol]])

## 4. ความทรงจำและบริบทต่อเนื่อง (Memory & Context)

- **หมอความจำ Memory Agent** (`question_resolver`) จะทำการรับคำถามสั้นๆ ด้วนๆ (follow-up) มาศัลยกรรมขยายให้เป็นประโยคที่สมบูรณ์ก่อนโยนให้ router สับราง + แถมมีการ์ดป้องกัน (guard) คอยตบตีหากหมอความจำดันปั้นประโยคยาวเว่อร์เกินเหตุ
- **แพ็กเกจประวัติ `history_context`** (แอบดึงประวัติแชทบน Redis มา 6 เทิร์น) ก้อนนี้จะถูกจับยัดแนบเข้าไปใน Task ของแทบทุกเส้นทาง pipeline — เพื่อบังคับให้เอเจนต์ตัวลึกๆ สามารถตอบโต้แบบต่อเนื่องไหลลื่นได้อารมณ์เหมือนกำลังคุยกับ Gemini/ChatGPT ตัวเป็นๆ
- **โครงร่างการตอบแบบ Obsidian:** ถ้าเป็นคำถามเปิดหัวครั้งแรก ระบบจะสาดคำตอบเต็มรูปแบบ 3 ส่วนจัดเต็ม, แต่ถ้าเป็นคำถามตามหลัง (follow-up) มันจะรู้ทัน และตอบแบบกระชับ หันไปเจาะลึกเฉพาะประเด็นที่ผู้ใช้ถามจี้เพิ่ม

## 5. การตั้งค่าสติปัญญา (Temperature & โมเดล)

| ระดับสติปัญญา (Tier) | อุณหภูมิ (Temp) | เหตุผลในการเลือก |
|---|---|---|
| โหมด Fast (ใช้ flash-lite) | 0.1 | ทีมงมค้นหา/ทีมดูดเดต้า/ทีมปั่นโค้ด — ต้องการคนที่อารมณ์นิ่ง สงบ และผลลัพธ์แม่นยำเป๊ะๆ |
| โหมด Pro (ใช้ 2.5-pro) | 0.2 | ทีมเรียบเรียงภาษา — อนุญาตให้มีความยืดหยุ่นในการใช้ภาษาสละสลวยได้เล็กน้อย |
| ทีมหมอความจำ (Memory Agent) | 0.1 | ต้องการให้ขยายความคำถามแบบซื่อๆ คงเส้นคงวา ห้ามไปใส่สีตีไข่คำถามผู้ใช้ |
| 🆕 **ทั้งท่อ CSV (`_get_llm()`)** | **0.1 (ล็อกแล้ว)** | เดิม**ไม่ได้ล็อกเลย** ปล่อยตาม default → agent เลือกโฟลเดอร์กับ relevance verifier ตอบไม่ตรงกันระหว่างรอบ ทั้งที่คำถามและ context เหมือนเดิมทุกตัวอักษร ตอนนี้บังคับใช้กับทุกตัวในท่อ (folder nav / relevance verifier / schema / code-gen / insight) |

## 6. ⚠️ รูรั่วช่องว่างที่ยังหลงเหลือ — ความตายตัว (Determinism) (ปัญหาท้าทายหลักในเฟส 2)

> [!warning] เรายังจับมันมัดล็อกผลลัพธ์ให้ "นิ่ง" 100% ไม่ได้ (🆕 คืบไปหนึ่งก้าวแล้ว)
> **อัปเดต:** ท่อ CSV ถูกล็อก `temperature=0.1` เรียบร้อยแล้ว (เดิมปล่อยตาม default) — แต่ **0.1 ยังไม่ใช่ 0** โค้ดเองยังคงคอมเมนต์กำกับไว้ตรง ๆ ว่ายังต้องมี safety net ถามซ้ำสูงสุด 2 ครั้งใน relevance gate เพราะ "โอกาสตอบไม่ตรงกันระหว่างรอบยังมีอยู่เล็กน้อย"
> ในเวอร์ชันปัจจุบัน เรา **ยังไม่ได้ตั้งค่าอุณหภูมิ `temperature=0` แบบตายตัว + ยังไม่ได้ล็อกเลข `seed` + แถมยังไม่ได้สลักล็อก (pin) เวอร์ชันโมเดลเป๊ะๆ** ทั่วทั้งระบบ →
> ส่งผลให้การพิมพ์คำถามเดิมเป๊ะๆ 2 ครั้ง อาจได้การเรียบเรียงคำตอบที่สวิงต่างกันนิดๆ หน่อยๆ ซึ่งทำให้การทำข้อสอบวัดผล (Benchmark/Trust) แบบรันซ้ำๆ ทำได้ยากเหนื่อยแสนเข็ญ
> - ❌ เรายังขาดระบบ **แคชคำตอบ (response cache)** (ที่ควรใช้คีย์ = hash(พรอมต์+บริบท corpus+โมเดล))
> - ❌ เรายังขาดระบบ **ดึงข้อมูลแบบล็อกเป้าหมาย (deterministic retrieval)** (ล็อกอันดับการค้นหาเนื้อหา chunk ให้อยู่นิ่งๆ)
> - ⚠️ ระบบ **ประเมินผลอัตโนมัติ (evaluation harness)** — ยังไม่มีของจริงแบบ Ragas **แต่เริ่มมีเชื้อแล้ว**: `tests/test_obsidian_fullcontext.py` มีคลาส `TestRunObsidianAskFullcontextGoldenSet` ที่จำลอง Gemini ตอบเนื้อหาดิบหลุด แล้วยืนยันว่า guard+retry เอาอยู่ — เป็น golden-set ขนาดจิ๋วที่ mock LLM ไว้ ยังไม่ใช่การวัดคุณภาพคำตอบจริง
>
> ภารกิจท้าทายเหล่านี้แหละ คือ **ภารกิจ Epic E1 (Determinism) และ E13 (Eval Harness)** ที่ต้องลุยต่อใน Phase 2
> (ซึ่งถูกเก็บเอกสารแผนงานไว้ใน companion vault `musya-obsidian-document` อีกตลับนึง) — ย้อนกลับไปดูเป้าหมายได้ที่ [[00 - Architecture Overview]] ส่วนที่ 6

## 7. สรุปหลักปรัชญาการออกแบบ (Design Principles)

1. **Grounded, not generated** — ตัวเลขสถิติทุกตัว ต้องผุดขึ้นมาจากรันไทม์ SQL/โค้ด/และหน้าเอกสารของจริงเท่านั้น
2. **AI decides meaning, code guarantees identity** — เราแบ่งงานตามกระดูก: ปล่อยให้ AI ตีความความหมาย แต่ต้องใช้กฎของโค้ดโปรแกรมเป็นตัวยืนยันหลักฐานจับคู่เสมอ
3. **Fail loud, not silent** — ไม่พบข้อมูล/ หรือถามผิดเขตสุขภาพ ต้องประกาศโวยวายให้ผู้ใช้รู้ตัวชัดเจน ห้ามแอบนั่งเดาสุ่มเอาใจผู้ใช้เด็ดขาด
4. **Cite everything** — คำอ้างอิงทุกประโยค ต้องผูกสายสะดือกลับไปยังแหล่งต้นทางให้ได้ (ไม่ว่าจะเป็นระบบ APA/ชื่อโน้ต/หรือลิงก์ URL)
5. **Continuity** — ระบบต้องมีความจำ ผูกพันคุยต่อเนื่องจากประเด็นเดิมได้จริงสมกับความเป็นบอทแชท
