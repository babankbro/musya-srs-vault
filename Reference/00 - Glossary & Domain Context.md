# 📖 อภิธานศัพท์และบริบทสาธารณสุขไทย (Glossary & Domain Context)

← กลับไป [[index|หน้าหลัก]] · เริ่มต้นที่นี่: [[00 - Setup & Onboarding Guide]]

> เอกสารฉบับนี้รวบรวม "คำศัพท์เฉพาะทาง" ที่ปรากฏกระจายอยู่ทั่วทั้งวอลต์ (Vault) นี้ — ไม่ว่าจะเป็นคำย่อฝั่ง **สาธารณสุข**, **กรอบวิเคราะห์นโยบาย (Frameworks)**, **ศัพท์เทคนิค IT**, ไปจนถึง **แหล่งที่มาของข้อมูล**
> จุดประสงค์คือเพื่อเป็นพจนานุกรมให้ผู้อ่านนอกวงการ (เช่น โปรแกรมเมอร์) เข้าใจบริบทการทำงานของเจ้า MUSYA AI ในสายตานักวิชาการสาธารณสุขครับ

---

## 1. องค์กร & โครงสร้างสาธารณสุขไทย (Organizations)

| คำศัพท์ / ตัวย่อ | ความหมายและบทบาทในระบบ |
|---|---|
| **เขตสุขภาพที่ 10** | (Health Region 10) กลุ่ม 5 จังหวัดเป้าหมายที่ระบบนี้ให้บริการครอบคลุม ได้แก่ อุบลราชธานี, ศรีสะเกษ, ยโสธร, อำนาจเจริญ, และมุกดาหาร |
| **สสจ.** | (สำนักงานสาธารณสุขจังหวัด / Provincial Public Health Office) — นี่คือ **ผู้ใช้งานหลัก (End-Users) และผู้บริหารเป้าหมาย** ที่จะเอารายงานจาก AI ไปใช้วางแผนนโยบายจริง |
| **ศปถ.** | (ศูนย์อำนวยการความปลอดภัยทางถนน / Road Safety Directing Center) — หน่วยงานหลักที่เกี่ยวข้องกับข้อมูลโดเมน `d1` อุบัติเหตุทางถนน |
| **สสส.** | (สำนักงานกองทุนสนับสนุนการสร้างเสริมสุขภาพ / ThaiHealth) — องค์กรหลักที่เป็นสปอนเซอร์ผู้สนับสนุนทุนของโครงการนี้ |
| **รายงานตรวจราชการ** | เอกสารทางการของกระทรวงสาธารณสุข ที่รายงานผลงานตามรอบการตรวจ (AI จะดึงรูปแบบนี้มาใช้ปั้นรายงานยุทธศาสตร์) |
| **ม.อุบลฯ (UBU)** | มหาวิทยาลัยอุบลราชธานี — เจ้าของโครงการและผู้ริเริ่มวิจัยระบบ MUSYA AI |

## 2. โดเมนสุขภาพในระบบ (Health Domains) — `domains.py`

| รหัสโค้ด | โดเมน (หมวดหมู่) | ความครอบคลุมของเนื้อหา |
|---|---|---|
| `d0` | ทั่วไป (General) | ใช้เมื่อผู้ใช้ถามกว้างๆ, เป็นที่ปรึกษาสุขภาพข้ามโดเมน หรือทักทายเล่นๆ |
| `d1` | อุบัติเหตุทางถนน (RTI) | จำนวนคนเจ็บ/ตายบนถนน, การวิเคราะห์จุดเสี่ยง (Black Spot) — ขุมทรัพย์ข้อมูลจะอยู่ในรูปแบบตาราง SQL star schema |
| `d2` | สุขภาพจิต (Mental Health) | ภาวะซึมเศร้า, สถิติการฆ่าตัวตาย, การเข้าถึงบริการจิตเวช — โดเมนที่เหลือจะวิเคราะห์โดยทุบไฟล์ CSV |
| `d3` | โรคไม่ติดต่อ (NCDs) | กลุ่มโรคเรื้อรังยอดฮิต เช่น เบาหวาน, ความดันโลหิตสูง, โรคหัวใจ, โรคหลอดเลือดสมอง |
| `d4` | โภชนาการ (Nutrition) | ภาวะทุพโภชนาการ, โรคอ้วนในเด็ก, ความมั่นคงทางอาหาร |
| `dt` | งานวิจัย ThaiJo | หมวดพิเศษสำหรับเจาะอ่านงานวิจัยและสังเคราะห์วรรณกรรมวิชาการของไทย |
| `obsidian` | คลังความรู้ (Vault) | ห้องสมุดเก็บเอกสารนโยบาย/รายงานการประชุมของเขต 10 (อ่านเป็นไฟล์ `.md`) |

## 3. กรอบวิเคราะห์นโยบาย (Policy Frameworks) — ที่เอเจนต์นำไปใช้จริง

| ชื่อกรอบคิด | ความหมาย | จุดที่ถูกเรียกใช้ในระบบ |
|---|---|---|
| **Haddon Matrix** | ตารางตรรกะสำหรับวิเคราะห์อุบัติเหตุ โดยตัดขวาง 3 ช่วงเวลา (ก่อน/ขณะ/หลังเกิดเหตุ) × 3 ปัจจัย (คน/ยานพาหนะ/สิ่งแวดล้อม) | ใช้โดย Zone10 Policy Analyst ใน ([[06 - Report & Policy Agents]]) |
| **BSC** | (Balanced Scorecard) — กรอบประเมินผลและวางแผนตัวชี้วัดเชิงยุทธศาสตร์แบบสมดุล 4 ด้าน | ใช้ในเอเจนต์วิเคราะห์แผน Plan Analyzer (workplan) |
| **PDCA** | (Plan-Do-Check-Act) — วงจรเดมิ่งสำหรับการพัฒนาคุณภาพงานอย่างต่อเนื่อง | ใช้ปั้นโครงเอกสารนโยบาย (ในเฟส 2) |
| **SWOT** | การวิเคราะห์สภาพแวดล้อม: จุดแข็ง (Strengths) / จุดอ่อน (Weaknesses) / โอกาส (Opportunities) / อุปสรรค (Threats) | ใช้เป็นโครงสร้างเนื้อหาในรายงาน |
| **Six Building Blocks (6BB)** | องค์ประกอบระบบสุขภาพ 6 เสาหลัก (อ้างอิงจากองค์การอนามัยโลก WHO) | ใช้เขียนข้อเสนอเชิงโครงสร้างในรายงานนโยบาย |
| **Policy Brief / Strategy Plan / Work Plan** | คือ "ประเภทของเอกสาร" ที่ระบบสามารถสร้างได้ (รหัส `doc_type`: `policy`/`plan`/`workplan`) | ดูขั้นตอนปั้นเอกสารได้ที่ [[06 - Report Generation Workflow]] |

## 4. แหล่งข้อมูล (Data Sources)

| ชื่อแหล่งข้อมูล | คำอธิบาย |
|---|---|
| **ThaiJo (TCI)** | ศูนย์ดัชนีการอ้างอิงวารสารไทย (Thai Journal Citation Index) — ฐานข้อมูลที่รวบรวมงานวิจัยภาษาไทยไว้มากที่สุด |
| **PubMed / NCBI** | ฐานข้อมูลวรรณกรรมและบทความวิจัยทางการแพทย์ระดับโลก (ดึงผ่าน E-utilities API) |
| **Tavily** | เอ็นจิ้นบริการค้นหาเว็บไซต์ระดับโลก (Web Search) ที่ออกแบบมาเพื่อป้อนให้ AI สรุปผลโดยเฉพาะ |
| **HDC** | (Health Data Center) ระบบคลังข้อมูลสุขภาพของกระทรวงสาธารณสุข — แหล่งดึงตัวชี้วัดสุขภาพรายพื้นที่ |
| **NHES** | (National Health Examination Survey) การสำรวจสุขภาพประชาชนไทยโดยการตรวจร่างกาย |
| **Open-Meteo** | บริการพยากรณ์อากาศสภาพแวดล้อมฟรี (ใช้ประกอบใน weather tool) |
| **Obsidian Vault** | คลังความรู้ส่วนตัวของโปรเจกต์ เก็บไฟล์ Markdown (`.md`) ของเขต 10 (ดึงสืบค้นผ่านตาราง `obsidian_notes`) |

## 5. ศัพท์เทคนิคคนไอที (Technical IT Terms)

| คำศัพท์ | ความหมายในบริบทระบบนี้ |
|---|---|
| **BFF** | (Backend-for-Frontend) — หมายถึงเซิร์ฟเวอร์ชั้นกลางของ Next.js ที่ทำหน้าที่คอยตรวจบัตร (auth) ก่อนสับราง (proxy) ไปหลังบ้าน (ดู [[02 - Frontend Design]]) |
| **SSE** | (Server-Sent Events) — เทคนิคพ่นข้อมูลทางเดียว ทำให้เห็นตัวหนังสือค่อยๆ พิมพ์โชว์บนหน้าจอทีละนิด (ดู [[01 - SSE Event Protocol]]) |
| **RAG** | (Retrieval-Augmented Generation) — ท่ามาตรฐาน AI ยุคใหม่: บังคับให้ AI ต้องไปงัดหลักฐานจริงมาอ่านก่อน แล้วค่อยสรุปตอบ |
| **CrewAI** | เฟรมเวิร์กจัดการทีม AI (multi-agent) แบ่งเป็น: ตัวละคร (Agent), ทีม (Crew), และภารกิจ (Task) |
| **litellm** | ไลบรารีอรรถประโยชน์ ที่ช่วยแปลงคำสั่งให้เรียกใช้ LLM ได้ทุกค่ายด้วยมาตรฐานเดียว (ใช้ตอนสตรีมข้อมูล) |
| **pgvector / pg_trgm** | ส่วนเสริม (extension) ของ PostgreSQL: ใช้เสิร์ชค้นหาข้อความภาษาไทยแบบตัดคำเสี้ยวๆ (trigram partial-match) |
| **star schema** | โมเดลการออกแบบคลังข้อมูล (Data Warehouse) แบบแบ่งตรงกลางเป็น fact แล้วล้อมด้วย dimension (ดู [[04 - Data Architecture & Schema]]) |
| **mart / dim / fact** | ศัพท์ดาต้า: `mart` = ตารางสรุปพร้อมใช้ / `dim` (dimension) = มิติป้ายกำกับ / `fact` = ข้อเท็จจริง ตัวเลขดิบๆ |
| **MinIO** | ระบบเก็บไฟล์ (Object Storage) ที่หน้าตาและการใช้งานโคลนนิ่งมาจาก Amazon S3 (ใช้เก็บไฟล์ CSV และ PDF) |
| **hotspot_score** | คะแนนความเสี่ยงการเกิดอุบัติเหตุซ้ำซากของพื้นที่หรือถนนสายนั้นๆ |
| **APA** | รูปแบบมาตรฐานการเขียนบรรณานุกรมอ้างอิงเอกสารวิชาการ (American Psychological Association) |
| **MOC** | (Map of Content) — โน้ตหน้าสารบัญที่ทำหน้าที่เป็นดัชนีเชื่อมโยงไปยังหน้าอื่นๆ ใน Obsidian |
| **RTI** | (Road Traffic Injury) — การบาดเจ็บ/สูญเสียที่เกิดจากอุบัติเหตุทางถนน |

## 6. คำที่มักจะทำให้สับสนบ่อย (Common Confusions)

| ศัพท์ที่สับสน | คำอธิบายเพื่อล้างบางความสับสน |
|---|---|
| **พ.ศ. ↔ ค.ศ.** | ในตารางฐานข้อมูล เราเก็บข้อมูลปีเป็น **ค.ศ. ล้วนๆ (2021–2026)**; แต่ผู้ใช้หน้าจอจะพิมพ์ถามเป็น **พ.ศ.** เสมอ → ระบบมีหน้าที่แปลงเอา −543 ก่อนยิงคิวรี และค่อยเอา +543 กลับไปคืนร่างตอนแสดงผลหน้าจอ (อ้างอิง [[03 - Functional Requirements|FR-CHAT-09]]) |
| **tool vs mode vs domain** | 3 คำนี้คนละชั้นกัน: *tool* = ปุ่มที่ผู้ใช้กดบนหน้าจอ → *mode* = ตัวแปรกำกับเส้นทางในฝั่ง Backend → *domain* = หมวดสุขภาพเฉพาะทางที่ตัว Router แอบวิเคราะห์และเลือกให้ (ดู [[02 - Frontend Design]]) |
| **out-of-zone guard** | ด่านยามตรวจจับหน้าประตู (Guard) หากเจอคำถามเกี่ยวกับจังหวัดที่อยู่นอกเขตสุขภาพที่ 10 → ยามจะปฏิเสธคำถามทันที (ห้ามใจดีแอบเอาข้อมูลจังหวัดอื่นในเขตมาสวมรอยตอบเด็ดขาด) |
| **agent vs pipeline vs crew** | *agent* = นักแสดง 1 คน (ตัวละคร LLM) · *crew* = กลุ่มนักแสดงที่ถูกจัดคิวให้ทำงานต่อๆ กัน · *pipeline* = สายพานการทำงานตั้งแต่ต้นจนจบของ 1 เครื่องมือ (เช่น CSV pipeline) |
