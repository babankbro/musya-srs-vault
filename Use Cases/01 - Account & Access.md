← [[00 - Actors & Use-Case Map]] · กลับไปยัง SRS: [[03 - Functional Requirements]]

## UC-01 — ลงทะเบียนบัญชีผู้ใช้งาน (Register account)

- **ผู้ดำเนินการ (Actor):** บุคคลทั่วไป (Guest) 
- **เป้าหมาย (Goal):** สร้างบัญชีส่วนตัวใหม่เพื่อเข้าใช้งานระบบ MUSYA
- **เงื่อนไขเริ่มต้น (Preconditions):** ยังไม่ได้เข้าสู่ระบบ; และอีเมลนั้นยังไม่เคยถูกนำมาลงทะเบียนในระบบ
- **จุดกระตุ้น (Trigger):** ผู้ใช้กรอกข้อมูลแล้วกดยืนยันในหน้าฟอร์ม `/register`

**ขั้นตอนหลัก (Main flow)**
1. บุคคลทั่วไปเข้าสู่หน้า `/register` เพื่อกรอกชื่อ, อีเมล, รหัสผ่าน และอาจกรอกข้อมูลส่วนตัวเพิ่มเติม (เช่น องค์กรที่สังกัด, ตำแหน่งงาน, พื้นที่จังหวัด, รหัสเขตสุขภาพ เป็นต้น)
2. ระบบทำการตรวจสอบความถูกต้องของข้อมูล (Validation) และเช็คว่าอีเมลนั้นไม่ซ้ำในระบบ
3. ระบบจะทำการเข้ารหัสผ่านในรูปแบบ bcrypt-12 ให้ปลอดภัยและบันทึกลงในฐานข้อมูลพร้อมสร้างบัญชีในระดับสิทธิ์ `role=user` และล็อกสถานะให้เป็น `status=pending` (รอตรวจสอบ)
4. ระบบตอบรับการลงทะเบียน และแสดงข้อความแจ้งผู้ใช้ว่า "การเข้าสู่ระบบจะต้องได้รับการตรวจสอบอนุมัติจากผู้ดูแลระบบก่อน"

**สถานการณ์ข้อยกเว้น (Alternate / exception)**
- 2a. **อีเมลซ้ำ:** หากพบอีเมลเดิมในระบบ → ระบบแจ้ง Error "อีเมลนี้ถูกลงทะเบียนไว้แล้ว" (ไม่มีการสร้างบัญชี)
- 2b. **ข้อมูลอ่อน/ไม่ถูกต้อง:** ข้อมูลรหัสผ่านสั้นเกินไปหรือผิดฟอร์แมต → ระบบแจ้ง Validation error พร้อมรีเซ็ตฟอร์มกลับไปให้แก้ใหม่

**เงื่อนไขสุดท้าย (Postconditions):** มีบัญชีใหม่ระดับรออนุมัติ (`pending`) ถูกสร้างในระบบ และต้องรอเข้าสู่การทำ [[#UC-05 — Approve or manage users|UC-05]]
**อ้างอิงถึงข้อกำหนด:** FR-AUTH-01, FR-AUTH-02, FR-AUTH-03.

## UC-02 — การเข้าสู่ระบบ (Log in)

- **ผู้ดำเนินการ (Actor):** บุคคลทั่วไป → กลายเป็น ผู้ใช้งาน (User) 
- **เป้าหมาย (Goal):** เริ่มต้นสร้างเซสชันการทำงานที่ปลอดภัย
- **เงื่อนไขเริ่มต้น (Preconditions):** มีบัญชีอยู่ในระบบแล้ว และบัญชีนั้นมีสถานะผ่านการอนุมัติ (`approved`)
- **จุดกระตุ้น (Trigger):** ผู้ใช้กดปุ่มตกลงในหน้า `/login`

**ขั้นตอนหลัก (Main flow)**
1. ผู้ใช้กรอกอีเมล + รหัสผ่าน เข้าไปที่หน้า `/login`
2. ระบบค้นหาบัญชีและตรวจสอบว่าบัญชีอยู่ในสถานะเปิดสิทธิ์ (`approved`) หรือไม่
3. ระบบตรวจสอบรหัสผ่านว่าตรงกับ Hash ในระบบหรือไม่
4. หากถูกต้อง ระบบจะสั่งสร้าง JWT (เข้ารหัสด้วย HS256, มีอายุยืนยาว 7 วัน) และฝังมันไว้ใน HttpOnly cookie ซึ่งเบราว์เซอร์เข้าถึงไม่ได้
5. ผู้ใช้จะถูกระบบส่งตัว (Redirect) ไปหน้าแอปหลัก (เช่น `/chat`); ถือเป็นการเปิดประตูด่านหน้า (Middleware) อย่างเป็นทางการ

**สถานการณ์ข้อยกเว้น (Alternate / exception)**
- 2a. **สถานะ = pending (ยังไม่อนุมัติ):** → ระบบเตะออก 403 "บัญชียังรอการอนุมัติอยู่"
- 2b. **สถานะ = rejected (ถูกปฏิเสธ):** → ระบบเตะออก 403 "บัญชีนี้ถูกปฏิเสธไม่ให้เข้าใช้งาน"
- 3a. **รหัสผ่านผิด:** → ระบบแจ้งกว้างๆ "ข้อมูลเข้าระบบไม่ถูกต้อง" (จะไม่มีการบอกว่ารหัสผิดหรืออีเมลผิด เพื่อกันคนสุ่มโจมตี: no user enumeration)
- 5a. **ระบบลืมตั้งกุญแจ `JWT_SECRET`:** → เกิด Server error กะทันหัน; การเข้าสู่ระบบจะถูกบล็อกเพื่อความปลอดภัยโดยเจตนาตามกฎระเบียบ (NFR-SEC-02)

**เงื่อนไขสุดท้าย (Postconditions):** มีคุกกี้บันทึกสิทธิ์ที่ถูกต้องติดอยู่กับตัวผู้ใช้ ทำให้สามารถเข้าหน้าความลับในระบบได้
**อ้างอิงถึงข้อกำหนด:** FR-AUTH-04, FR-AUTH-05, FR-AUTH-09, NFR-SEC-01, NFR-SEC-02, NFR-SEC-03.

### ตัวอย่างสถานการณ์จำลอง — เจ้าหน้าที่ผ่านการอนุมัติและเข้าสู่ระบบ
> `musya01@gmail.com` กรอกรหัสผ่าน → สถานะเป็น `approved`, รหัส Hash ตรงกัน → ระบบตั้งค่าคุกกี้ `auth_token` → ส่งตัวไปที่ `/chat` พร้อมลิสต์รายการแชทก่อนหน้าโชว์ขึ้นที่แถบข้าง

## UC-03 — รีเซ็ตรหัสผ่าน (Reset password)

- **ผู้ดำเนินการ (Actor):** บุคคลทั่วไป (Guest)
- **เป้าหมาย (Goal):** สามารถกู้คืนการเข้าถึงระบบได้เมื่อลืมรหัส
- **เงื่อนไขเริ่มต้น (Preconditions):** ต้องมีอีเมลที่เคยสมัครทิ้งไว้ในระบบ
- **จุดกระตุ้น (Trigger):** ผู้ใช้กรอกอีเมลที่หน้า `/forgot-password`

**ขั้นตอนหลัก (Main flow)**
1. ผู้ใช้ระบุอีเมลตนเองที่หน้าฟอร์ม `/forgot-password`
2. ระบบตรวจสอบพบแล้วแอบสร้างโทเค็นพิเศษ `reset_token` และกำหนดวันเวลาหมดอายุลงในฐานข้อมูล
3. ผู้ใช้คลิกปุ่มผ่านลิ้งก์ที่ได้รับในอีเมลและทำการกำหนดรหัสผ่านชุดใหม่
4. ระบบเช็คโทเค็นว่าถูกต้อง/ไม่หมดอายุ จึงเปลี่ยนอัปเดตรหัสผ่านใหม่แบบ Hash และทำลายล้างโทเค็นนั้นทิ้ง (เพื่อไม่ให้ถูกนำมาใช้ซ้ำ)

**สถานการณ์ข้อยกเว้น (Alternate / exception)**
- 4a. **โทเค็นหมดอายุ/โดนใช้ไปแล้ว:** → โชว์ Error; ผู้ใช้ต้องเริ่มกดขอรีเซ็ตอีเมลใหม่ตั้งแต่ข้อแรก
- 1a. **อีเมลไม่พบในระบบ:** → ระบบแกล้งทำเป็นบอกว่า "ส่งข้อความยืนยันเรียบร้อยแล้ว" แบบเป็นกลางๆ (เพื่อป้องกันคนมั่วสุ่มหาอีเมลในฐานข้อมูล)

**เงื่อนไขสุดท้าย (Postconditions):** รหัสผ่านเก่าถูกเปลี่ยนใหม่ โทเค็นที่ใช้หมดค่าลง
**อ้างอิงถึงข้อกำหนด:** FR-AUTH-07, DR-LIFE-03.

## UC-04 — แก้ไขข้อมูลโปรไฟล์ (Edit profile)

- **ผู้ดำเนินการ (Actor):** ผู้ใช้งาน (User)
- **เป้าหมาย (Goal):** เพื่ออัปเดตข้อมูลหน่วยงานและตำแหน่งปัจจุบัน
- **เงื่อนไขเริ่มต้น (Preconditions):** กำลังอยู่ในระบบ (Logged in)
- **จุดกระตุ้น (Trigger):** ผู้ใช้เปิดเข้าไปหน้าเมนู `/account`

**ขั้นตอนหลัก (Main flow)**
1. ผู้ใช้งานเรียกดูข้อมูลส่วนตัวเดิมของตนเองที่แสดงขึ้นมา
2. ผู้ใช้งานทำการพิมพ์แก้ข้อมูลบางช่องที่เปิดให้แก้ไขได้ (เช่น องค์กร, เขตจังหวัด, ตำแหน่ง) จากนั้นกดปุ่มบันทึก (Save)
3. ระบบจะบันทึกข้อมูลทับรอยเดิม (`updated_at` จะทำงานผ่านกลไก Trigger ในดาต้าเบส)

**เงื่อนไขสุดท้าย (Postconditions):** ข้อมูลใหม่ผู้ใช้มีผลเรียบร้อย
**อ้างอิงถึงข้อกำหนด:** FR-AUTH-08.

## UC-05 — อนุมัติหรือจัดการบัญชีผู้ใช้งาน (Approve or manage users)

- **ผู้ดำเนินการ (Actor):** แอดมินสูงสุด (Admin Super)
- **เป้าหมาย (Goal):** รักษาความปลอดภัยและเลือกให้สิทธิ์เฉพาะผู้ปฏิบัติงานที่แท้จริง
- **เงื่อนไขเริ่มต้น (Preconditions):** ล็อกอินและครอบครองสิทธิ์ `adminsuper`
- **จุดกระตุ้น (Trigger):** แอดมินคลิกเข้าเมนู `/approved`

**ขั้นตอนหลัก (Main flow)**
1. แอดมินเปิดแผงรายชื่อบัญชีขึ้นมาพร้อมกรองเช็คสถานะ/ระดับบทบาท (Role)
2. เลือกที่บัญชีสถานะรออยู่ (`pending`) และทำการกดเลือกระหว่าง **อนุมัติ (Approve)** หรือ **ปฏิเสธ (Reject)**
3. ในกรณีที่กด อนุมัติ (Approve) ระบบจะเซ็ตให้กลายเป็น `status=approved` พร้อมบันทึกหลักฐานไว้ด้วยว่า `approved_by` ใครเป็นคนกดรับและเวลาใด
4. บัญชีที่ได้รับการอนุมัติ ก็สามารถเดินเรื่องเข้าแอปพลิเคชันได้ในระบบปกติต่อไป ([[#UC-02 — Log in|UC-02]])

**สถานการณ์ข้อยกเว้น (Alternate / exception)**
- 0a. **มีคนอื่นที่ไม่ใช่แอดมินหลงเข้ามาหน้านี้ `/approved`:** → ระบบตัดทิ้งแจ้ง Access denied แม้จะล็อกอินมาถูกต้อง (สกัดด้วยด่าน Role check)
- 2a. **กด ปฏิเสธ (Reject):** → สถานะบัญชีเปลี่ยนเป็น `status=rejected`; คนผู้นั้นก็ยังคงเข้าแอปไม่ได้เหมือนเดิม

**เงื่อนไขสุดท้าย (Postconditions):** สถานะบัญชีเป้าหมายเปลี่ยนไป และบันทึกรอยเท้าคนตรวจสอบเรียบร้อย
**อ้างอิงถึงข้อกำหนด:** FR-ADMIN-01, FR-ADMIN-02, FR-ADMIN-03, NFR-SEC-05.

### ตัวอย่างสถานการณ์จำลอง — การพิจารณารับข้าราชการใหม่เข้าทำงาน
> มีนักวิชาการสาธารณสุขใหม่เพิ่งลงทะเบียนมา (UC-01, ติดสถานะ `pending`) → ผู้ดูแลระดับสูง (Admin Super) เปิดแผงควบคุมที่ `/approved` และกดพิจารณาอนุมัติ (Approve) → ระบบสแตมป์ชื่อคนอนุมัติใน `approved_by` → เจ้าหน้าที่คนนั้นจึงมีสิทธิ์เข้าแอป (UC-02) จนสามารถไปถึงหน้าหลักอย่าง `/chat` ได้สำเร็จ
