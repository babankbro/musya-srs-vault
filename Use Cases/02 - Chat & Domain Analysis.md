# 💬 กรณีการใช้งานระบบแชทและการวิเคราะห์ข้อมูลโดเมน (Chat & Domain Analysis)

← [[00 - Actors & Use-Case Map]] · กลับไปที่ SRS: [[03 - Functional Requirements]] · ดูสถาปัตยกรรม: [[02 - Overall Description]]

> **หมายเหตุสำคัญ:** กรณีการใช้งานในหมวดนี้ทุกข้อยึดโยงอยู่กับแกนกลางเดียวกัน คือ: **การยืนยันตัวตนจาก BFF → การทำ Proxy → Memory Agent (ความจำแชท) → Router Agent (ตัวแยกทาง) → เข้าท่อ Pipeline → สตรีมผลลัพธ์ผ่าน SSE → เก็บบันทึกลงฐานข้อมูล** ซึ่งแต่ละเคสจะต่างกันตรงที่เครื่องมือ/โหมด ที่ผู้ใช้เลือก

---

## UC-06 — ถามคำถามทั่วไปแบบปกติ (Ask a question - normal mode)

- **ผู้ดำเนินการ:** ผู้ใช้งาน (User) 
- **เป้าหมาย:** ต้องการได้คำตอบที่อ้างอิงหลักฐานทางสุขภาพได้โดยไม่ต้องใช้เครื่องมือเจาะจง
- **เงื่อนไขเริ่มต้น:** อยู่ในหน้าจอ `/chat`
- **จุดกระตุ้น:** ผู้ใช้พิมพ์ข้อความถามและกดส่ง (โดยไม่ได้กดปุ่ม Tool ตัวช่วยใดๆ)

**ขั้นตอนหลัก (Main flow)**
1. หน้าเว็บ (UI) จะยิง `POST /api/chat` พร้อมกับบอกสถานะ `mode=normal`, ระบุ `sessionId`, `prompt` (คำถาม) และประวัติ `history`
2. ระบบด่านหน้า BFF ทำการตรวจรหัส JWT หากผ่านก็จะฝัง `x-internal-key` นำทางทะลวงไปหา `POST /api/analyze` ของ Backend ทันที
3. หากว่ามีประวัติการแชทเดิมค้างอยู่ เอเจนต์ความจำ (**Memory Agent**) จะนำประวัติมาขยายข้อความคำถามใหม่ให้สมบูรณ์ขึ้น (เช่น คำถามกำกวมอย่าง "แล้วอำเภอเมืองล่ะ" จะถูกแก้เป็น "สถิติของอำเภอเมืองมีอะไรบ้าง")
4. เอเจนต์คัดแยกทิศทาง (**Router Agent**) จะวิเคราะห์และแบ่งหมวด (Domain); กรณีถ้าเป็นคำถามเชิงอุบัติเหตุ (`d1`) ในโหมดปกติ ระบบจะฉลาดพอที่จะหักเหคำถามนี้ไปรันบนกระบวนการความรู้ของ **Obsidian** (ให้ตอบข้อมูลเชิงทฤษฎี/นโยบาย แทนที่จะไปกวนฐานข้อมูล SQL หาตัวเลข)
5. ท่อการทำงาน Pipeline จะเริ่มทำงาน พร้อมส่งสัญญาณการเกิด (`agent_start`/`agent_done`) แสดงให้ผู้ใช้เห็นว่าใครกำลังทำอะไร
6. คำตอบชิ้นสุดท้ายถูกทยอยส่งกลับมา (Stream) หน้าจอเริ่มประมวลผลข้อความและวาดเอกสารอ้างอิงและคำถามแนะนำต่อเนื่อง (Follow-ups) ขึ้นมา
7. ระบบฝั่งหลังบ้านจะเซฟประวัตินี้เข้าไปใน Redis และฝั่ง BFF เซฟประวัติถาวรลงฐานข้อมูล

**สถานการณ์ข้อยกเว้น**
- 2a. **Token หมดอายุ/ไม่พบ:** → เกิดรหัส 401; หน้าจอเด้งกลับไปหน้าล็อกอิน
- 4a. **คำถามควบหลายหัวข้อ:** → ระบบจะเปิดท่อขนาน (Multi-domain pipeline) แยกวงกันทำงาน
- 5a. **ชนลิมิตเครื่องทำงานหนักเกิน:** → ระบบขึ้นข้อความขออภัยกำลังยุ่ง (FR-CHAT-15)
- 5b. **เน็ตมือถือหลุด หรือผู้ใช้ปิดหน้าเว็บหนี:** → ระบบทำกระบวนการสำรองอัตโนมัติ (Fallback) วิ่งคำนวณต่อจนจบแล้วแอบเซฟเก็บเข้าฐานข้อมูลเงียบๆ (FR-CHAT-14)

## UC-07 — ดึงข้อมูลสถิติอุบัติเหตุ (เขตสุขภาพที่ 10)

- **ผู้ดำเนินการ:** ผู้ใช้งาน (User)
- **เป้าหมาย:** ดึงตัวเลขและสถิติการเกิดอุบัติเหตุบนท้องถนนเจาะจงจังหวัดและปี
- **เงื่อนไขเริ่มต้น:** อยู่ในแชท; กดปุ่มเครื่องมือ **สถิติ** ทิ้งไว้
- **จุดกระตุ้น:** ผู้ใช้พิมพ์สั่งงาน เช่น *"ขอสถิติอุบัติเหตุอุบลราชธานี ปี 2567"*

**ขั้นตอนหลัก**
1. หน้าจอรับรู้ส่งค่า `mode=stats`
2. ตัว Router จับทางได้ว่าเป็นเรื่องอุบัติเหตุ (วัดจากคีย์เวิร์ด หรือให้ LLM วิเคราะห์)
3. ระบบแกะชื่อ **จังหวัด** และทำการแปลงปีจาก **พ.ศ. เป็น ค.ศ.** (เช่น 2567 → 2024 ทันที)
4. เอเจนต์ฐานข้อมูลอุบัติเหตุ (**Accident SQL Agent**) วิ่งเข้าคิวรี (Query) ชุดตาราง Star schema โดยตรง (หาสรุปเทรนด์, จุดเสี่ยง, ถนนอันตราย)
5. ผลลัพธ์ตอบกลับเป็นรูปแบบตาราง (Markdown tables) พร้อม **เชิงอรรถข้อจำกัดของข้อมูล (Data-limitation footnotes)**

**สถานการณ์ข้อยกเว้น**
- 2a/3a. **ถามจังหวัดผิดที่ (เช่น ขอนแก่น):** ไม่มีจังหวัดในเขต 10 อยู่ในรูปประโยคเลย → ระบบตัดบททันที แจ้งอย่างชัดเจนว่า "ไม่มีข้อมูลของพื้นที่นี้" พร้อมขึ้นรายชื่อ 5 จังหวัดเป้าหมายที่แท้จริง (FR-CHAT-08)
- 3b. **ไม่ได้ระบุปีมาให้:** → ระบบใจดี กวาดข้อมูลช่วงปี 2021–2026 ทั้งหมดให้
- 4a. **ถามเชิงลึกเกินไป (เช่น อายุ/เพศ/หมวกกันน็อก):** → ระบบจะหาข้อมูลไม่เจอ และชี้แจงในเชิงอรรถข้อจำกัดว่า ข้อมูลระดับบุคคล (ตาราง `fact_accident_person`) ขณะนี้ยังว่างเปล่า (CON-7)

## UC-08 — ดึงข้อมูลสถิติจากหมวดไฟล์ CSV (สุขภาพจิต / NCD / โภชนาการ)

- **ผู้ดำเนินการ:** ผู้ใช้งาน (User)
- **เป้าหมาย:** ทำการวิเคราะห์เจาะลึกตัวชี้วัด (Indicator) ผ่านไฟล์ CSV ในโดเมน `d2–d4`
- **เงื่อนไขเริ่มต้น:** ล็อกอินแล้ว; กดปุ่มเครื่องมือ **สถิติ**; เป็นคำถามที่ไม่เกี่ยวกับการเกิดอุบัติเหตุ
- **จุดกระตุ้น:** ผู้ใช้ถาม เช่น *"ความชุกเบาหวานยโสธรเทียบปีที่ผ่านมา"*

**ขั้นตอนหลัก**
1. หน้าจอส่งสถานะ `mode=stats` เข้าสู่ระบบ
2. Router คัดแยกประเภทตกหมวด `d2/d3/d4` (และแยกว่าถามไฟล์เดียว หรือ เทียบกันหลายไฟล์)
3. ระบบจะรัน **CSV pipeline** (ประกอบด้วย 6 Agent ทำงานประสานกัน): หาเป้าหมายไฟล์ CSV ในเซิร์ฟเวอร์ MinIO → อ่านตารางโครงสร้าง → เขียนโค้ดไพทอน → ส่งไปรันในกระบะทรายจำลอง (Isolated subprocess) → สรุปผล
4. ข้อสรุปและความหมายที่จับต้องได้ รวมถึงตัวเลขจะสตรีมส่งกลับให้ผู้ใช้

**สถานการณ์ข้อยกเว้น**
- 3a. **หาไฟล์ไม่เจอ หรือ มีชื่อคล้ายกันมากไป:** → กระบวนการสุ่มเดา Fuzzy อาจหาไม่เจอ ระบบยอมแพ้และเลือกบอกความจริงว่าหาชุดข้อมูลไม่พบ ดีกว่าไปนั่งเทียนนั่งสร้างตัวเลขมั่วๆ ขึ้นมา
- 2a. **ถามหลายเรื่องพร้อมกัน:** → จะตกไปเข้าช่อง Multi-CSV pipeline (ค้นหาไฟล์ตามแผนผังโฟลเดอร์ + เชื่อมด้วยกุญแจพื้นที่ + ตรวจเช็คซ้ำ)

## UC-09 — ถามคำถามแบบอิงคลังความรู้องค์กร (Ask the knowledge vault)

- **เป้าหมาย:** ถามหาคำตอบที่ยืนยันด้วยงานนโยบายหรือวิชาการที่ถูกอัปโหลดรวมในเขต 10
- **จุดกระตุ้น:** ผู้ใช้เปิดเครื่องมือ **คลังความรู้รายงาน** และเริ่มถามคำถาม

**ขั้นตอนหลัก**
1. UI รับเรื่องแล้วส่ง `mode=obsidian`
2. ระบบจะพยายามจับชื่อจังหวัดในประโยค เพื่อเอาไปจำกัดกรอบบริบทให้แคบลง ป้องกันคำตอบหลงทาง
3. เข้าสู่สายท่อ **Obsidian full-context** (เอาข้อมูลดิบทั้งหมดที่ค้นพบอัดเข้าใส่หัว Gemini ให้พิจารณา)
4. สตรีมคำตอบส่งพร้อมกับ **กล่องอ้างอิงต้นฉบับเอกสารโน้ต** และกล่อง **แนะนำแนวทางคำถามต่อไป**

## UC-10 — เครื่องมือเจาะลึกงานวิจัย (Research: ThaiJo / PubMed)

- **เป้าหมาย:** สกัดรวบรวมเนื้อหาเชิงวรรณกรรม/วิชาการการแพทย์ เพื่อนำมาสังเคราะห์
- **จุดกระตุ้น:** ผู้ใช้เปิดเครื่องมือ **วิจัย** เลือกแหล่งที่มา (ThaiJo, PubMed, หรือควบรวมคู่) แล้วส่งคำถาม

**ขั้นตอนหลัก**
1. ฝั่ง UI ส่งข้อมูลเข้า Backend แยกสถานะตามที่กด: ควบรวมคู่ = `research`, หาเฉพาะในไทย = `thaijo`, หางานอินเตอร์ = `pubmed`
2. โหมดการควบรวม (`research`) จะทำการจุดประกายให้ท่อ ThaiJo และ ท่อ PubMed ออกตัวไปพร้อมกัน **ขนานกัน (in parallel)**
3. ข้อมูลที่หาได้ (ชื่อบทความ, ผู้แต่ง, ลิ้งก์ URL, บทคัดย่อ) จะพุ่งกลับเข้ามา
4. ระบบจับสองแหล่งรวมกัน สตรีมรายชื่อและสรุปเล็กๆ ออกมาฝั่งซ้ายของจอ และสตรีมตัวเต็มอ่านยาวๆ ไว้ฝั่งขวาของจอ

## UC-11 — การใช้เครื่องมือสืบค้นเว็บทั่วไป (General web search)

- **เป้าหมาย:** หาบริบท ข่าวสาร และข้อมูลปัจจุบันทันด่วนผ่านอินเทอร์เน็ต
- **จุดกระตุ้น:** ผู้ใช้เปิดเครื่องมือ **ค้นหาทั่วไป**

**ขั้นตอนหลัก**
1. UI ส่งพารามิเตอร์ `mode=tavily`
2. เอเจนต์ **Tavily pipeline** จะออกไปท่องเว็บ (โดยบีบกรอบการค้นหาให้เน้นเนื้อหาประเทศไทยเป็นหลัก) และให้ Agent ตัวเขียนสรุปทำการอ้างอิงให้
3. แต่ละแหล่งข้อมูลเว็บ (URLs) จะถูกแปะป้ายเก็บเข้ากระเป๋าไว้ เผื่อผู้ใช้จะเอามันไปใช้สร้าง Report ในภายหลัง

## UC-12 — แชทต่อในเซสชันเดิม (Continue a chat session)

- **เป้าหมาย:** หยิบยกเรื่องที่คุยค้างไว้เมื่อวาน หรือสัปดาห์ก่อนมาคุยสานต่อและอ้างบริบทเดิม
- **จุดกระตุ้น:** ผู้ใช้เปิดหน้าลิงก์เซสชันเก่า `/chat/sessions/[sessionId]` หรือกดเรียกเมนูที่แถบด้านข้าง

**ขั้นตอนหลัก**
1. UI วิ่งไปดึงประวัติบทสนทนา (State messages) ออกมาจากฐานข้อมูลหลัก
2. ผู้ใช้ตั้งคำถามต่อยอด (ตัวอย่างเช่น *"แล้วแยกรายอำเภอล่ะ"*)
3. **Memory Agent** ก็จะกางข้อความเก่าที่ดึงมา ทบทวนอดีต แล้วแต่งประโยคเป็นคำถามที่สมบูรณ์ขึ้นด้วยโดเมนเดิม
4. ท่อการทำงาน Pipeline วิ่งรับช่วงต่อจนจบ แล้วแปะบันทึกใหม่ต่อท้าย Session เดิม

**สถานการณ์ข้อยกเว้น**
- 1a. **ไม่ใช่เซสชันตัวเอง (เผลอกดลิ้งก์ชาวบ้าน):** → ระบบป้องกันสิทธิ์ ไม่อนุญาตให้โหลดข้อมูล
- 3a. **เรื่องที่คุยมันเก่าเกินกว่า 24 ชม.:** → ประวัติใน Redis ถูกลบไปแล้ว แต่ไม่มีปัญหา ระบบจะพลิกแพลงไปค้นเอาประวัติระยะยาวใน `chat_sessions` ของฐานข้อมูลมาเป็นตัวทบทวนให้แทน
