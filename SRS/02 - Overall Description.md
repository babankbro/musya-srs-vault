# 2. ภาพรวมของระบบ (Overall Description)

← [[01 - Introduction & Scope]] · → [[03 - Functional Requirements]]

## 2.1 มุมมองของผลิตภัณฑ์ (Product perspective)

MUSYA AI ถูกออกแบบมาภายใต้ **สถาปัตยกรรมแบบ 2 ชั้น (Two-tier web system)** และถูกติดตั้งใช้งานจริง (Deployed) โดยแยกเป็น **5 บริการบน Docker Compose (Five Docker Compose services)**
ระบบแบ่งการทำงานระหว่าง Frontend ที่ทำหน้าที่แสดงผลหน้าจอ (UI) และเป็น Backend-for-Frontend (BFF) สำหรับจัดการสิทธิ์ผู้ใช้ ในขณะที่ฝั่ง Python Backend ทำหน้าที่เป็น "สมอง" AI แบบเพียวๆ ผู้ใช้หรือบุคคลภายนอกจะไม่สามารถเข้าถึงการทำงานของ Backend ได้โดยตรงเด็ดขาด — ฝั่ง BFF จะเป็นด่านหน้าคอยคัดกรองทุกคำขอเสมอ

```text
                       ┌─────────────────────────┐
   Browser ──:3000──►  │  frontend (Next.js 16)  │  chatapp-frontend
                       │  UI + BFF + Auth (JWT)  │
                       └───────────┬─────────────┘
                                   │ proxy (x-internal-key)
                                   │ PYTHON_API_URL=http://python-ai:8000
                       ┌───────────▼─────────────┐
   Swagger ──:8000──►  │  python-ai (FastAPI)    │  chatapp-python-ai
                       │  CrewAI agents + tools  │
                       └───┬───────┬───────┬─────┘
                           │       │       │
              ┌────────────▼─┐ ┌───▼────┐ ┌▼──────────┐
              │ postgres     │ │ minio  │ │ redis     │
              │ pgvector:pg16│ │ files  │ │ chat hist │
              └──────────────┘ └────────┘ └───────────┘
```

| ชื่อบริการ (Service) | เทคโนโลยีหลัก (Tech) | พอร์ต (Port) | ความรับผิดชอบหลัก (Responsibility) |
|---|---|---|---|
| frontend | Next.js 16 / React 19 / TS / Tailwind 4 | 3000 | แสดงผล UI + ระบบ BFF (การเข้าสู่ระบบ, ประวัติแชท, เอกสาร, ไฟล์อัปโหลด) + ตัวส่งต่อข้อมูล (Proxy) ไปหา Backend |
| python-ai | FastAPI + Uvicorn + CrewAI + litellm | 8000 | ระบบสมอง AI (Agents), ชุดคำสั่งไปป์ไลน์ (Pipelines) และเครื่องมือต่างๆ โดยจะสตรีมผลลัพธ์ผ่านโปรโตคอล SSE |
| postgres | `pgvector/pgvector:pg16` | 5432 | ฐานข้อมูลหลัก จัดเก็บข้อมูลผู้ใช้งาน, สถิติอุบัติเหตุแบบ Star schema และดัชนีคลังความรู้ Obsidian สำหรับระบบ RAG |
| minio | `minio/minio` | 9000/9001 | ฐานข้อมูลแบบ Object Storage ใช้สำหรับเก็บไฟล์ที่ผู้ใช้อัปโหลด (CSV/PDF/DOCX) และเอกสารอ้างอิง APA |
| redis | `redis:7-alpine` | 6379 | ระบบหน่วยความจำแคชสำหรับจัดเก็บประวัติแชทย้อนหลัง (เก็บ 6 ข้อความล่าสุด, ลบออกใน 24 ชั่วโมง) และการทำแคชระบบ |

## 2.2 โมเดลการประมวลผลระดับสูง (High-level processing model)

ทุกคำถาม หรือคำสั่งวิเคราะห์ข้อมูลของผู้ใช้ จะไหลผ่านกระบวนการหลักตามแกนกลาง (Fixed Spine) ดังนี้:

```text
ผู้ใช้พิมพ์คำถาม + กดเลือกเครื่องมือ (Tool)
      │  POST /api/chat (BFF ร้องขอ, เข้ารหัส JWT) → ทำ Proxy → เรียก POST /api/analyze (ไปยัง Backend)
      ▼
Memory Agent (ผู้จัดการหน่วยความจำ) ← นำคำถามไปเชื่อมต่อและขยายผลกับประวัติการแชทเดิมใน Redis
      ▼
Router Agent (ตัวคัดแยกเส้นทาง) ← ทำการจัดประเภทโดเมนว่าเข้าข่าย d0–d4/dt/obsidian และเลือกว่าเป็นคำถามเดี่ยว/รวม
      ▼
การเลือกเส้นทาง Pipeline ย่อยอ้างอิงจากข้อมูลโดเมน (Domain) และโหมด (Mode) ที่ได้:
      ├ หมวดอุบัติเหตุ (d1 accident)      → วิ่งเข้าสู่ Accident-SQL pipeline (ค้นใน PostgreSQL รูปแบบ star schema โดยตรง)
      ├ หมวดอื่นๆ (d2–d4) แบบข้อมูลเดี่ยว → วิ่งสู่ CSV pipeline (มี 6 Agent: ค้นหา→ดูโครงสร้าง→เขียนโค้ด→รัน→สรุป)
      ├ หมวดอื่นๆ (d2–d4) แบบข้อมูลรวม    → วิ่งสู่ Multi-CSV pipeline (จับคู่ข้อมูลจากหลายแฟ้ม + ดึงกุญแจพื้นที่ + ตรวจสอบ)
      ├ หมวดงานวิจัย (dt research)      → วิ่งเข้า ThaiJo pipeline (ค้นหา→วางแผน→สร้างเนื้อหา) และ/หรือ PubMed
      ├ หมวดความรู้ภายใน (obsidian)     → วิ่งสู่ Obsidian full-context pipeline (โหลดไฟล์ .md → สรุปด้วย Gemini)
      ├ หมวดค้นหาทั่วไป (tavily)        → เข้าสู่ระบบ Web-search pipeline
      └ หมวดสร้างรายงาน (report-gather) → สั่งทุกช่องทางรันขนานพร้อมกัน 5 ทิศทาง → รวมผลลัพธ์ → เข้าสู่ Report Wizard
      ▼
เริ่มส่งคืนผลลัพธ์ (SSE Events): เหตุการณ์เช่น เริ่มทำงาน / ส่งข้อความบางส่วน / ส่งผลลัพธ์ย่อย / ผลลัพธ์สุดท้าย / หรือแจ้งข้อผิดพลาด
      ▼
การบันทึก: ระบบจะบันทึกลง Redis ฝั่ง Backend พร้อมเซฟประวัติฝั่ง BFF; หากผู้ใช้กดเซฟ ระบบจะสร้าง journal_reports เพื่อนำออกไฟล์
```

## 2.3 ผู้ใช้งานระบบและลักษณะผู้ใช้ (User classes and characteristics)

- **เจ้าหน้าที่สาธารณสุข และ นักกำหนดนโยบาย (Primary users):** ผู้ใช้กลุ่มเป้าหมายหลัก สนทนาเป็นภาษาไทย เป็นผู้เชี่ยวชาญด้านสาธารณสุขแต่ไม่ได้มีทักษะทางเทคนิคขั้นสูง (Non-technical) ให้ความสำคัญกับความรวดเร็ว, การอ้างอิงที่ถูกต้องแม่นยำ และเอกสารผลลัพธ์ที่มีรูปแบบมาตรฐาน หน้าตาแอป (UI) ออกแบบโดยให้ความสำคัญกับภาษาไทยเป็นหลัก (ใช้ฟอนต์ IBM Plex Sans Thai)
- **ผู้ดูแลระบบสูงสุด (Administrators - `adminsuper`):** เจ้าหน้าที่ไอที หรือผู้ดูแลโครงการ มีหน้าที่คอยตรวจสอบอนุมัติบัญชีผู้ใช้ใหม่ จัดการบทบาทผู้ใช้งาน และเปิดสิทธิ์การเข้าถึงข้อมูลให้ผู้ใช้งานแต่ละราย
- **นักวิจัยและนักวิเคราะห์ (Researchers/analysts):** สามารถใช้ระบบเชิงลึก อย่างเมนูเครื่องมือฐานข้อมูล (DB Explorer) และสืบค้นงานวิจัยเฉพาะทาง เพื่อวิเคราะห์ข้อมูลขั้นสูง

## 2.4 สภาพแวดล้อมการทำงาน (Operating environment)

- **ระบบฝั่งเซิร์ฟเวอร์ (Server):** ใช้งานบนเทคโนโลยี Docker Compose ในรูปแบบ Linux Containers บนเซิร์ฟเวอร์ที่ติดตั้ง Docker Desktop หรือ Docker Engine
- **ฝั่งไคลเอนต์ (Client):** ใช้งานผ่านเบราว์เซอร์เดสก์ท็อปรุ่นใหม่ จำเป็นต้องรองรับเทคโนโลยี SSE และคุกกี้ (Cookies) เพื่อการเชื่อมต่อและส่งผ่านข้อมูลแบบเรียลไทม์
- **ปัญญาประดิษฐ์ (LLM):** ใช้ **Google Gemini** เป็นแกนหลักในการวิเคราะห์ประมวลผล (`gemini-2.5-flash-lite`, หรือ `-pro` เมื่อจำเป็น) เรียกใช้งานผ่านไลบรารี litellm; รองรับ OpenAI เป็นระบบสำรอง มีระบบ API อื่นๆ ที่ใช้งานคือ: ThaiJo, PubMed/NCBI, Tavily, และ Open-Meteo

## 2.6 ข้อจำกัดด้านการออกแบบและการพัฒนา (Design & implementation constraints)

- **CON-1 — ขอบเขตเชิงภูมิศาสตร์ (Geographic scope):** ข้อมูลจะมีเพียง 5 จังหวัดในเขตสุขภาพที่ 10 เท่านั้น; คำสั่งที่ร้องขอพื้นที่นอกเขต จะต้องแจ้งกลับอย่างชัดเจนว่า "ไม่มีข้อมูล" เสมอ
- **CON-2 — รูปแบบปี (Year encoding):** ฐานข้อมูลบันทึกเป็นปี ค.ศ. (2021–2026); หากผู้ใช้ถามด้วยปี พ.ศ. ระบบจะต้องทำการบวก-ลบ (±543) ก่อนค้นหา
- **CON-3 — การเข้าถึงระบบภายใน (Internal auth):** บริการ Backend จะไม่ถูกเปิดให้เชื่อมต่อกับโลกอินเทอร์เน็ตโดยตรง จะเชื่อถือเพียงคำขอที่ส่งมาจาก BFF พร้อมรหัส `x-internal-key` เท่านั้น
- **CON-4 — ข้อจำกัดความหนาแน่นของการวิเคราะห์ (Concurrency cap):** ระบบถูกตั้งค่า (BoundedSemaphore) ให้รัน AI Pipelines ได้ไม่เกิน **5 ทิศทางพร้อมกัน ต่อ 1 เวิร์กเกอร์ (Worker)** หากเกินกว่านี้ ระบบจะส่ง SSE ข้อความ "ระบบไม่ว่าง (Busy)" กลับไปยังผู้ใช้งาน
- **CON-5 — โควต้าการใช้ LLM (LLM rate limits):** กรณีติดโควต้าหรือเซิร์ฟเวอร์ของ Gemini ล่ม (รหัส 429/503) ระบบมีการทำ Bounded Exponential Backoff เพื่อหน่วงเวลา และกระบวนการ report-gather จะทิ้งช่วงเวลาสลับกันเรียก 1.5 วินาที เพื่อกันการส่ง Request ถี่เกินไป
- **CON-6 — บริบทสูงสุดที่ระบบรับได้ (Context window):** บริบทความรู้ใน Obsidian ถูกกรองเอาเฉพาะจังหวัดที่ตรงกับเงื่อนไข และจะถูกตัดความยาว (Capped) จำกัดไว้ที่ `OBSIDIAN_MAX_CONTEXT_CHARS = 500,000` เพื่อป้องกันเซิร์ฟเวอร์ Gemini Error "Context Overflow"
- **CON-7 — ข้อจำกัดของโครงสร้างฐานข้อมูล (Empty data surfaces):** ตารางข้อมูลอุบัติเหตุบางจุด (เช่น `fact_accident_person` บุคคลที่เกิดเหตุ) ปัจจุบันยังว่างเปล่า และ `road_name` ส่วนใหญ่มักเป็นค่าความว่างเปล่า (NULL) หากผู้ใช้ถามถึงหมวดหมู่นี้ ระบบต้องแสดงผลอธิบายถึงข้อจำกัดของข้อมูลเสมอ

## 2.8 สมมติฐานและสิ่งที่ระบบพึ่งพา (Assumptions & dependencies)

- ต้องมีกุญแจ API (API Keys) สำหรับ Gemini (และอาจรวมถึง Tavily/OpenAI/NCBI) ระบุอยู่ในไฟล์ตั้งค่า `.env` อย่างครบถ้วน
- ระบบฐานข้อมูล PostgreSQL ต้องติดตั้งโครงสร้างตารางข้อมูล (Schema) ครบถ้วน รวมถึงมีข้อมูลดิบของตารางอุบัติเหตุ และถูกดัชนีพร้อมใช้ร่วมกับ Obsidian Vault
- ต้องมีการกำหนดค่า `JWT_SECRET` และ `INTERNAL_API_KEY` ให้ตรงกันทั้งในบริการส่วนหน้า (BFF) และบริการส่วนหลัง (Backend) (สำหรับการใช้งาน Production ต้องมีการเปลี่ยนค่า Default ให้มีความปลอดภัยสูงสุด — อ้างอิง [[05 - Non-Functional Requirements|NFR-SEC]])
- บนระบบ MinIO จะต้องมีระบบ Bucket ที่ชื่อ `fileapa` และ `pdf-library` สำหรับเก็บข้อมูลสร้างไว้ล่วงหน้า
