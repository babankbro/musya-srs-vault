# 3. ความต้องการด้านฟังก์ชันการทำงาน (Functional Requirements)

← [[02 - Overall Description]] · → [[04 - External Interface Requirements]]

> **หมายเหตุ:** รหัสอ้างอิง (IDs) ใช้เพื่อระบุตัวตนในเชิงเทคนิค และอ้างอิงไปถึง [[00 - Actors & Use-Case Map|แผนผัง Use cases]] รวมถึงช่วยให้ง่ายต่อการวางแผนทดสอบระบบในอนาคต
> **ระดับความสำคัญ (Priority):** **M** = บังคับต้องมี (Mandatory - ลงมือทำเรียบร้อย), **S** = ควรมี (Should), **C** = อาจจะมีในอนาคตหรือทำเพียงบางส่วน (Could/partial)

---

## 3.1 การตรวจสอบสิทธิ์และการจัดการบัญชีผู้ใช้ (Authentication & Account Management: `FR-AUTH-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-AUTH-01 | บุคคลทั่วไป (Guest) **จะต้อง (shall)** ลงทะเบียนบัญชีใหม่ด้วย ชื่อ, อีเมล, รหัสผ่าน และข้อมูลโปรไฟล์ทางเลือก (องค์กร, ตำแหน่ง, จังหวัด, เขตสุขภาพ เป็นต้น) โดยอีเมลต้องไม่ซ้ำกันในระบบ | M |
| FR-AUTH-02 | บัญชีผู้ใช้งานใหม่ **จะต้อง** มีระดับสิทธิ์ตั้งต้นเป็น `role=user`, สถานะการอนุมัติเป็น `status=pending` (รอตรวจสอบ) และจะไม่สามารถลงชื่อเข้าใช้ระบบได้จนกว่าผู้ดูแลระบบจะกดอนุมัติ | M |
| FR-AUTH-03 | รหัสผ่าน **จะต้อง** ถูกเข้ารหัสและจัดเก็บในรูปแบบ bcrypt hashes (ความเข้มข้นระดับ 12) ไม่อนุญาตให้ระบบเก็บรหัสผ่านในรูปแบบข้อความดิบ (Plaintext) เด็ดขาด | M |
| FR-AUTH-04 | ผู้ใช้งาน **จะต้อง** ลงชื่อเข้าใช้ด้วย อีเมล และ รหัสผ่าน; เมื่อยืนยันสำเร็จ ระบบจะทำการสร้างและออกกุญแจเข้ารหัส JWT (HS256, อายุใช้งาน 7 วัน) ฝังไว้ใน HttpOnly Cookie อย่างปลอดภัย | M |
| FR-AUTH-05 | การล็อกอิน **จะต้อง** ถูกปฏิเสธ หากผู้ใช้นั้นยังมีสถานะ `status ∈ {pending, rejected}` พร้อมแสดงข้อความเตือนชัดเจน (HTTP 403 Forbidden) | M |
| FR-AUTH-06 | ผู้ใช้ **จะต้อง** สามารถออกจากระบบ (Log out) ได้ และคุกกี้ข้อมูลที่ยืนยันตัวตนจะถูกลบออกจากเบราว์เซอร์โดยสมบูรณ์ | M |
| FR-AUTH-07 | บุคคลทั่วไป **จะต้อง** สามารถร้องขอเพื่อรีเซ็ตรหัสผ่านผ่านอีเมลได้ โดยระบบจะออก `reset_token` ที่มีอายุการใช้งานจำกัดส่งไปยังอีเมล โทเค็นนี้ใช้งานได้เพียงครั้งเดียว เมื่อเปลี่ยนรหัสผ่านเสร็จจะหมดอายุทันที | M |
| FR-AUTH-08 | ผู้ใช้งาน **จะต้อง** สามารถดูภาพรวมข้อมูลส่วนตัวและกดแก้ไขข้อมูลบัญชีของตนเองได้ (หน้าเว็บ `/account`) | M |
| FR-AUTH-09 | ทุกหน้าเว็บและทุกเส้นทาง API ที่เป็นความลับ **จะต้อง** ตรวจสอบและกรอง JWT Token อย่างเคร่งครัด การเข้าถึงที่ไม่มีการยืนยันตัวตนจะต้องถูกส่งกลับไปยังหน้าล็อกอิน (`/login`) หรือแจ้ง 401 Unauthorized สำหรับฝั่ง API | M |

## 3.2 ระบบบริหารจัดการสำหรับผู้ดูแลระบบ (User Administration: `FR-ADMIN-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-ADMIN-01 | ผู้ดูแลระดับสูง (`adminsuper`) **จะต้อง** สามารถดูรายการผู้ใช้งานทั้งหมด รวมถึงสถานะและสิทธิ์บทบาท (Role) ของผู้ใช้งานแต่ละคนผ่านทางหน้า `/approved` ได้ | M |
| FR-ADMIN-02 | ผู้ดูแลระดับสูง (`adminsuper`) **จะต้อง** สามารถอนุมัติหรือปฏิเสธบัญชีผู้ใช้ที่รอดำเนินการ (Pending account) การอนุมัติจะต้องเก็บบันทึกข้อมูลระบุว่า "อนุมัติโดยใคร" (`approved_by`) และ "อนุมัติเมื่อไหร่" (`approved_at`) | M |
| FR-ADMIN-03 | พื้นที่บริหารจัดการ `/approved` **จะต้อง** สงวนสิทธิ์เข้าถึงไว้สำหรับผู้ที่มีบทบาท `role=adminsuper` เท่านั้น บทบาทอื่นๆ แม้ว่าจะล็อกอินอยู่แล้วจะต้องถูกปฏิเสธสิทธิ์ในการเข้าถึงส่วนนี้ | M |
| FR-ADMIN-04 | การดำเนินการใดๆ ของแอดมิน **จะต้อง** วิ่งผ่านเส้นทางหลักของ BFF (`/api/auth/users`) โดยต้องมีการยืนยันความปลอดภัยครบถ้วน | M |

## 3.3 แชทอัตโนมัติและการวิเคราะห์เชิงลึก (Chat & Domain Analysis: `FR-CHAT-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-CHAT-01 | ผู้ใช้ **จะต้อง** ส่งคำถามทางสุขภาพที่ใช้โครงสร้างประโยคทั่วไปเป็นภาษาไทยจากหน้าแชท และได้รับคำตอบจากการประมวลผลทยอยไหลกลับมาแบบสตรีมมิ่ง (Server-Sent Events: SSE) | M |
| FR-CHAT-02 | ผู้ใช้ **จะต้อง** มีสิทธิ์ในการกดเลือกตัวช่วยพิเศษ (Tool) ได้หนึ่งอย่างต่อ 1 คำถาม คือ: สร้างรายงาน, สถิติ, ค้นหาทั่วไป, วิจัย, หรือคลังความรู้รายงาน; หากไม่ระบุ ระบบจะรันการวิเคราะห์ในโหมดปกติแบบครอบจักรวาล (`normal` mode) | M |
| FR-CHAT-03 | เอเจนต์คลังความทรงจำ (**Memory Agent**) **จะต้อง** เข้าไปตรวจสอบประวัติการแชทย้อนหลังใน Redis (ดึงมา 6 ครั้งล่าสุด) และนำข้อความที่เกี่ยวข้องมาร้อยเรียงปรับแต่งบริบทให้มีความสมบูรณ์เพื่อให้ Router Agent เข้าใจได้ทันที | M |
| FR-CHAT-04 | เอเจนต์คัดแยกเส้นทาง (**Router Agent**) **จะต้อง** ทำหน้าที่คัดแยกคำถามไปยังหนึ่งโดเมน (หรือหลายโดเมน) รวมถึงระบุว่ากระบวนการนั้นจะต้องทำแบบชุดคำสั่งเดี่ยว (Single) หรือเชิงรวมหลายส่วน (Multi) | M |
| FR-CHAT-05 | สำหรับหมวดอุบัติเหตุ (`d1`, หรือระบุ Tool `สถิติ`) ระบบ **จะต้อง** สืบค้นจาก PostgreSQL แบบตารางฐานข้อมูล Star schema โดยตรง ส่งคำตอบออกมาเป็นรูปแบบตาราง Markdown ควบคู่กับคำอธิบายข้อจำกัดของข้อมูล (Footnotes) | M |
| FR-CHAT-06 | สำหรับหมวดอื่นๆ เชิงสถิติ (`d2–d4`) ระบบ **จะต้อง** ตามหาตำแหน่งไฟล์ CSV ที่ตรงหมวดใน MinIO สั่งสร้างโครงสร้างชุดคำสั่ง Python สั่งรันชุดคำสั่งวิเคราะห์ในสภาพแวดล้อมจำลอง (Subprocess แบบ Isolate) และสรุปความหมายจากข้อมูล | M |
| FR-CHAT-07 | ระบบ **จะต้อง** สามารถสตรีมสถานะและโปรเกสการทำงานของระบบประมวลผลกลับไปยังหน้าจอให้ผู้ใช้รับรู้ได้ (`agent_start`/`agent_done`) เพื่อให้เห็นภาพกระบวนการทำงานเบื้องหลัง | M |
| FR-CHAT-08 | ในกรณีที่ผู้ใช้ถามข้อมูลที่อ้างอิงพื้นที่จังหวัดนอกเขตสุขภาพที่ 10 (และไม่มีพื้นที่ในข่าย) ระบบ **จะต้อง** แจ้งผู้ใช้อย่างชัดเจนว่า "ไม่มีข้อมูลของพื้นที่ดังกล่าว" และระบุถึงชื่อจังหวัดเป้าหมายหลัก 5 แห่งให้ผู้ใช้ทราบ ห้ามทำการทดแทนหาจังหวัดในพื้นที่อื่นมามั่วแทนโดยเด็ดขาด | M |
| FR-CHAT-09 | ระบบ **จะต้อง** ทำการแปลงรูปแบบปีในคำถามจาก พ.ศ. ให้กลายเป็น ค.ศ. ทันทีเมื่อเข้าสู่หมวดอุบัติเหตุทางถนน เพื่อให้การเรียกดึงข้อมูลจากฐานแม่นยำที่สุด | M |
| FR-CHAT-10 | เครื่องมือวิจัย (`วิจัย`) **จะต้อง** เปิดทางเลือกให้ผู้ใช้ระบุแหล่งข้อมูล ว่าเป็น ThaiJo, PubMed, หรือควบรวมทั้งสองแห่ง โดยหากควบรวมระบบจะรัน 2 ท่อ (Pipelines) พร้อมกันแล้วจับผลมารวมกัน | M |
| FR-CHAT-11 | เครื่องมือทั่วไป (`ค้นหาทั่วไป`) **จะต้อง** สั่งให้ AI ลงไปทำ Web search แบบเรียลไทม์ (Tavily) ดึงความรู้มารวมเป็นคำตอบพร้อมคำอ้างอิงที่เหมาะสม | M |
| FR-CHAT-12 | เครื่องมือดึงข้อมูลภายใน (`คลังความรู้รายงาน`) **จะต้อง** ตอบคำถามโดยอ้างอิงจาก Obsidian Knowledge Vault ซึ่งจะต้องมีคำตอบ พร้อมแนบที่มาเอกสารย่อยที่ใช้งาน รวมถึงแนะนำแนวคำถามที่เกี่ยวเนื่อง | M |
| FR-CHAT-13 | ระบบ **จะต้อง** บันทึกประวัติการแชท (Chat sessions) เชื่อมตามรหัส `sessionId` และสามารถดึงลิสต์การแชทล่าสุดของผู้ใช้มาเปิดแสดงที่แถบเมนูด้านซ้าย เรียงลำดับจากใหม่สุดไปเก่าสุด | M |
| FR-CHAT-14 | หากอินเทอร์เน็ตหลุดกลางคัน หรือตัวเบราว์เซอร์ถูกปิดก่อนประมวลผลเสร็จ ฝั่ง BFF **จะต้อง** รอรับคำตอบสุดท้ายแล้วนำไปบันทึกลง Session ให้ครบถ้วน ป้องกันปัญหาประวัติค้างสถานะ "กำลังทำงาน (running)" แบบไม่มีจุดจบ | M |
| FR-CHAT-15 | เมื่อยอดผู้ใช้งานคำสั่งการวิเคราะห์เต็มโควต้าสูงที่สุด (Concurrency cap) ระบบ **จะต้อง** ตอบกลับด้วยข้อความแจ้งเตือนที่เป็นมิตร แทนที่จะทำเป็นโหลดหมุนค้าง | M |
| FR-CHAT-16 | ผู้ใช้งาน **ควรจะ (shall/should)** สามารถอัปโหลดไฟล์เข้ามาพร้อมกับคำถามในหน้าแชท ระบบควรอ่านไฟล์พร้อมเข้าสู่โหมด Database-Analysis ทันที | S |

## 3.4 เครื่องมือสร้างรายงาน (Report Generation: `FR-REPORT-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-REPORT-01 | เครื่องมือ `สร้างรายงาน` **จะต้อง** ใช้วิธีรวบรวมเนื้อหาจากหลายโดเมนพร้อมกันแบบคู่ขนาน (ดึงจาก Knowledge vault, ข้อมูลสถิติ, ThaiJo, PubMed, ระบบเว็บเพจทั่วไป) แล้วสตรีม "ข้อมูลตั้งต้นแบบเจาะลึก" เข้าไปโชว์ที่พาเนลหน้าจอฝั่งขวา | M |
| FR-REPORT-02 | ระบบ **จะต้อง** รองรับการออกรายงานระดับทางการทั้งหมด 3 รูปแบบ คือ: **สรุปภาพรวมนโยบาย (Policy Brief)**, **แผนแม่บท/ยุทธศาสตร์ (Strategy Plan)**, และ **แผนการดำเนินงานรายปี (Work Plan)** | M |
| FR-REPORT-03 | ต้องมีตัวช่วยสร้างแบบฟอร์ม (Wizard) ที่ผู้ใช้กดนำเนื้อหาข้อมูลมาประกอบโครงสร้างเป็นเอกสารรายงาน HTML ทางการแพทย์ที่ดูน่าเชื่อถือ พร้อมการระบุบรรณานุกรม (References) | M |
| FR-REPORT-04 | เมื่อมีการสืบค้นผ่าน ThaiJo pipeline โหมดนี้ **จะต้อง** สร้างเอกสารที่สรุปผลและรายงานจำนวนบทความทางวิชาการที่พบออกมาเป็น HTML artefact ด้วยตนเองได้ | M |
| FR-REPORT-05 | ผู้ใช้งาน **จะต้อง** สามารถกดบันทึกหน้าเอกสารรายงานนั้นลงในฐานข้อมูลชั้นเก็บส่วนตัว (`journal_reports`) โดยจะมีหัวข้อ, ชนิดของเอกสาร, รูปแบบคำสั่ง Query และโครงร่าง HTML ไว้เป็นข้อมูล | M |
| FR-REPORT-06 | ผู้ใช้งาน **จะต้อง** สามารถเข้ามาเปิดดู, เรียกดึง และลบหน้าเอกสารสรุปงานวิจัยและรายงายที่บันทึกไว้ได้จากหน้าเมนูหลักของแอป (`/journal`) | M |
| FR-REPORT-07 | ผู้ใช้งาน **จะต้อง** สามารถนำเอกสารที่สรุปนี้ แปลงออกมาเป็นไฟล์นามสกุล DOCX หรือ PDF จากเอกสาร HTML ดังกล่าวได้ | M |
| FR-REPORT-08 | การอ้างอิง (References) แต่ละแห่งของเอกสารรายงาน **ควรจะ** ถูกแยกตามแหล่งเนื้อหานั้น (แหล่งวิจัยแต่ละชิ้นจาก ThaiJo/PubMed/หน้าเว็บ) ไม่ใช่ถูกจับมัดรวมกันแบบลวกๆ | S |

## 3.5 คลังความรู้ระดับองค์กร (Knowledge Vault: `FR-KB-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-KB-01 | ระบบ **จะต้อง** มีระบบค้นหาเอกสารจากหน้าจอแบบทันใจผ่านคีย์เวิร์ด หรือวิธี Trigram search ครอบคลุมคลังความรู้ Obsidian ทั้งหมดโดยไม่ใช้ LLM เปลืองไฟเกินจำเป็น (`/api/obsidian/search`) | M |
| FR-KB-02 | ระบบ **จะต้อง** ใช้คำตอบจากบริบทเชิงลึกเต็มตัวอักษรของคลังเอกสาร (Vault) ได้ โดยจะต้องแบ่งเป็นรายจังหวัดไว้เพื่อกันการทำงานเกินขีดจำกัดหน่วยความจำของ LLM Context Window | M |
| FR-KB-03 | ผู้เชี่ยวชาญฝั่งปฏิบัติการระบบ (Operator) **จะต้อง** สามารถอัปเดตและใส่โครงสร้าง (Re-index) แฟ้มคลังความรู้ใหม่เข้าไปรันบน PostgreSQL ได้แบบง่าย (`obsidian_vaults/notes/chunks/links`) | M |
| FR-KB-04 | ผู้เชี่ยวชาญฝั่งปฏิบัติการระบบ (Operator) **จะต้อง** มีฟังก์ชันเพื่อดูดซับเชื่อมไฟล์เอกสาร PDF ดิบเข้าสู่เซิร์ฟเวอร์เก็บไฟล์ MinIO และทำสัญลักษณ์ความเชื่อมโยงกับ Note ข้อมูลได้ (`obsidian_pdf_assets`) | M |
| FR-KB-05 | ผู้ใช้ **จะต้อง** สามารถเรียกอ่านตัวเนื้อหาอ้างอิงจากโน้ต พร้อมลิ้งก์ให้ดาวน์โหลดดูตัว PDF ต้นฉบับได้โดยตรงจากหน้าจอระบบ (`/musyaend/obsidian`) | M |

## 3.6 การจัดการข้อมูลไฟล์ดิบและการอ้างอิง APA (File & Citation Management: `FR-FILE-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-FILE-01 | ผู้ใช้ **จะต้อง** มีเครื่องมือในการดึงเอกสารอัปโหลดไฟล์เข้าระบบได้ (รองรับ PDF/DOCX/CSV/XLSX) เพื่อไปจัดเก็บบน MinIO | M |
| FR-FILE-02 | ระบบ **จะต้อง** สร้างบรรณานุกรมให้อัตโนมัติตาม **โครงสร้างมาตรฐาน APA Citation** อาศัยข้อมูลที่แกะสกัด (Metadata) ดึงมาจากเอกสารนั้น (`/fileapa`, `/api/generate-apa`) | M |
| FR-FILE-03 | ผู้ใช้ **จะต้อง** เห็นลิสต์รายการเอกสาร พร้อมให้ข้อมูลเสริมที่ AI สกัดและจัดทำข้อมูลเจาะลึกออกมา สามารถเข้าชมและลบไฟล์ของตนเองได้ | M |
| FR-FILE-04 | ผู้ใช้ **ควรจะ** สามารถรวมเนื้อหาของหลายเอกสารเข้าด้วยกัน เพื่อสืบสวนและค้นหาคำตอบในระดับมหภาค (ค้นหา → วิเคราะห์ → ดึงข้อมูล → เซฟผลลัพธ์) กลายเป็นชุดข้อมูลใหม่ | S |
| FR-FILE-05 | ผู้ใช้ **ควรจะ** นำไฟล์ PDF ทั้งหมดโยนรวมไว้ในห้องสมุด (PDF Library) เพื่อแปลง (Chunking) เข้าสู่กระบวนการระบบ Vault index อัตโนมัติ | S |

## 3.7 ระบบสำรวจเชิงวิศวกรรมและความโปร่งใสของข้อมูล (Data Exploration & Observability: `FR-OPS-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) | ระดับ |
|---|---|---|
| FR-OPS-01 | ผู้ใช้ **จะต้อง** สามารถเลื่อนสำรวจดูตารางข้อมูลแบบเจาะจงที่ใช้ในการสร้างผลลัพธ์ได้ (โหมดอ่านอย่างเดียว: Read-only) ผ่านชุดเครื่องมือหน้า DB Explorer สามารถระบุหัวเรื่อง เช็คตาราง คอลัมน์ ลบค่าแสดงผลข้อมูลขนาดใหญ่ออกอัตโนมัติ (Vector fields) | M |
| FR-OPS-02 | ระบบปฏิบัติการ **จะต้อง** มีหน้าบันทึก Log ปัญหา (Errors) หรือสาเหตุการล้มเหลว แบ่งหมวดอย่างชัดเจน ไม่ว่าจะเกิดปัญหาจากการเข้ารหัส สิทธิ์เต็ม โควต้าล้น หรือ Timeout และเซฟลง Daily log files ในแต่ละวัน | M |
| FR-OPS-03 | ผู้ปฏิบัติงานเบื้องหลัง **จะต้อง** สามารถเข้ามาตรวจเช็ค และเรียกให้ AI ช่วยวิเคราะห์สรุปปัญหา Log errors พวกนั้นได้แบบกว้างๆ (`/api/errors`) | M |
| FR-OPS-04 | ระบบหลังบ้าน (Backend) **จะต้อง** ทำหน้าที่เปิดบริการตรวจสอบสถานะ (`GET /health`) และเปิด Swagger Documentation API (`/docs`) ให้แก่ฝั่ง Developer เข้าตรวจสอบการทำงาน | M |
