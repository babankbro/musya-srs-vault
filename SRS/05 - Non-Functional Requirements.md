# 5. ข้อกำหนดอื่นที่ไม่ใช่ฟังก์ชันหลัก (Non-Functional Requirements)

← [[04 - External Interface Requirements]] · → [[06 - Data Requirements]]

## 5.1 ประสิทธิภาพและการรองรับการขยายตัวของระบบ (Performance & scalability: `NFR-PERF-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) |
|---|---|
| NFR-PERF-01 | **การแสดงผลคำตอบต้องรวดเร็ว:** คำตอบจากระบบ AI **จะต้อง** สตรีมผลลัพธ์ทีละส่วนให้ผู้ใช้เห็นทันที (แสดงข้อความอัปเดตของ Agent แรกให้เห็นในเวลาไม่กี่วินาที) ห้ามปล่อยให้หมุนโหลดรอค้างแบบบล็อก (Blocking) จนกว่าจะวิเคราะห์เสร็จสมบูรณ์ |
| NFR-PERF-02 | **การจำกัดการทำงานขนาน:** จุดวิเคราะห์ (`analyze endpoint`) **จะต้อง** จำกัดการทำงานของ Pipeline ไม่ให้เกิน **5 ครั้ง ต่อ 1 ตัวเวิร์กเกอร์ (Worker)** (โดยใช้เทคนิค BoundedSemaphore) หากระบบแบกรับเกินโควต้านี้ ระบบจะส่งคำเตือน "ระบบยุ่งอยู่" ပြန်ไปยังผู้ใช้ (ดูเพิ่มเติมที่ [[03 - Functional Requirements|FR-CHAT-15]]) |
| NFR-PERF-03 | **กำหนดเวลาสูงสุด (Timeout):** ฝั่งระบบหลังบ้าน (BFF) **จะต้อง** เปิดช่องทางให้ระบบ AI คิดวิเคราะห์ได้นานสูงสุด **10 นาที** ต่อการขอ 1 คำถาม ก่อนที่จะทำการตัดการทำงานทิ้ง (Time out) |
| NFR-PERF-04 | **ความเร็วการค้นหาด่วน:** ข้อมูลอุบัติเหตุในโหมด "ค้นด่วน (Quick)" (`/quick`, `/zone10/data`) **ควรจะ** นำส่งข้อมูลแบบ SQL เพียวๆ ออกมาให้ผู้ใช้เห็นผลใน **น้อยกว่า 5 วินาที** โดยไม่ต้องวิ่งอ้อมไปเรียกใช้งานโมเดล AI (LLM) |
| NFR-PERF-05 | **ระบบรวบรวมรายงาน (Report-gather):** ระบบต้องหน่วงเวลาทิ้งช่วงการปล่อยงาน (Stagger) ให้เวิร์กเกอร์ 5 ตัวห่างกันทีละ ~1.5 วินาที เพื่อช่วยลดการยิง Request เข้าหา LLM จำนวนมากพร้อมกันในพริบตา ป้องกันปัญหา Quota Limit |
| NFR-PERF-06 | **การจำกัดบริบท Obsidian:** บริบทของ Obsidian ที่เตรียมโหลดเข้าสมอง LLM **จะต้อง** ถูกคัดกรองตามจังหวัด และจำกัดปริมาณตัวอักษรไม่ให้เกินพิกัดที่ `OBSIDIAN_MAX_CONTEXT_CHARS` (ประมาณ 500,000 ตัวอักษร) เพื่อป้องกันปัญหาข้อมูลทะลัก Context Window |

## 5.2 ความน่าเชื่อถือและความพร้อมใช้งาน (Reliability & availability: `NFR-REL-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) |
|---|---|
| NFR-REL-01 | **ระบบทนทานต่อ API ล่ม:** หาก Gemini แจ้งสถานะล้มเหลวกลับมา (รหัส 429/503) ระบบ **จะต้อง** พยายามทวนซ้ำโดยการหน่วงเวลาแบบทวีคูณ (Bounded exponential backoff: จำกัดให้พยายามสูงสุด 3 ครั้ง, โดยเริ่มหน่วง 8 วิ และสูงสุดไม่เกิน ~45 วิ) |
| NFR-REL-02 | **คำตอบที่ว่างเปล่า:** หาก LLM คืนค่าข้อความว่างเปล่ามา ระบบ **จะต้อง** ทวนซ้ำ หากเกิดซ้ำซาก ระบบจะต้องทำบันทึก (Logged) เก็บไว้ แต่ต้องไม่เด้งข้อผิดพลาดโชว์จนแอปพลิเคชันหน้าจอพัง (Crash) |
| NFR-REL-03 | **การปกป้องเซสชัน:** กรณีอินเทอร์เน็ตหลุดระหว่างที่ AI ตอบ ระบบ **จะต้อง** ไม่ปล่อยให้สถานะหน้าจอผู้ใช้ค้างว่า "กำลังรันงาน" ต่อไปเรื่อยๆ (BFF จะเซฟสถานะในตอนจบให้เสมอ - อ้างอิง [[03 - Functional Requirements|FR-CHAT-14]]) |
| NFR-REL-04 | **ระบบสำรวจสุขภาพการเชื่อมต่อ (Health checks):** ฝั่ง Docker services **จะต้อง** ประกาศเกณฑ์เช็คสุขภาพและมีลำดับการรันที่ถูกต้อง (เช่น ฐานข้อมูล postgres และ minio ต้องตื่นสมบูรณ์ก่อนจะปลุก python-ai; และ python-ai ต้องตื่นก่อน frontend) |
| NFR-REL-05 | **การเริ่มใหม่แบบยืดหยุ่น:** บริการทั้งหมด **จะต้อง** ถูกครอบด้วยคำสั่ง `restart: unless-stopped` ใน Docker เพื่อรีสตาร์ทตัวเองอัตโนมัติหากตายกลางคัน |

## 5.3 ความปลอดภัยและข้อมูลส่วนบุคคล (Security & privacy: `NFR-SEC-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) |
|---|---|
| NFR-SEC-01 | **ความปลอดภัยของ Session Token:** ต้องอยู่ในรูปแบบ JWT (เข้ารหัส HS256) และบันทึกลงใน **HttpOnly** cookie (โหมด `sameSite=lax`); ไม่อนุญาตให้ฝัง Token ใน `localStorage` เพื่อป้องกันการถูกขโมยจากภัยคุกคาม XSS |
| NFR-SEC-02 | **กุญแจเข้ารหัสลับ:** `JWT_SECRET` **จะต้อง** มีการกำหนดค่าไว้เสมอ มีความยาว ≥ 8 ตัวอักษร และไม่ใช่คำว่า Placeholder หากตั้งค่ามาไม่ดี แอปพลิเคชันจะไม่ยอมเข้ารหัสหรือทำงานด้วย |
| NFR-SEC-03 | **รหัสผ่านที่เก็บ:** รหัสผ่าน **จะต้อง** เข้ารหัสผ่าน bcrypt-hashed (ความเข้มข้นระดับ 12) |
| NFR-SEC-04 | **ซ่อนหลังบ้านให้มิดชิด:** ฝั่ง Backend **จะต้อง** รับเฉพาะคำขอที่มีการสอดไส้ `x-internal-key` มาด้วยเท่านั้น ผู้ใช้ทั่วไปภายนอกไม่มีสิทธิ์เข้าถึง Backend ได้เลย |
| NFR-SEC-05 | **ห้ามเข้าใช้งานข้ามสิทธิ์:** พื้นที่สำหรับผู้ดูแล (`adminsuper`) ต้องปฏิเสธผู้ใช้ในระดับสิทธิ์อื่นทั้งหมด แม้ว่าผู้ใช้นั้นจะเข้าสู่ระบบแบบถูกต้องแล้วก็ตาม |
| NFR-SEC-06 | **กฎหมาย CORS:** การอนุญาตการเข้าถึงข้ามโดเมน (CORS) **จะต้อง** ถูกล็อกไว้ให้เรียกจากโดเมนของ Frontend ที่ตั้งไว้เท่านั้น |
| NFR-SEC-07 | **ป้องกันการฉีดฐานข้อมูล:** ระบบ DB Explorer **จะต้อง** ทำหน้าที่อ่านฐานข้อมูลอย่างเดียว (Read-only) พร้อมมีการตรวจเช็คตัวอักษรที่เสี่ยงต่อการเกิด SQL Injection อย่างรัดกุม |
| NFR-SEC-08 (ช่องโหว่) | **สิ่งที่ต้องทำก่อนขึ้นระบบจริง (Before production):** เปลี่ยนกุญแจค่าเริ่มต้นของ `JWT_SECRET` / `INTERNAL_API_KEY` ลบรหัสผู้ใช้ตั้งต้นออกจากไฟล์ `schema.sql` และระบบยังขาดการคัดกรองข้อมูล PDPA ในไฟล์เอกสารของผู้ป่วยที่อัปโหลด ซึ่งต้องนำไปพิจารณาสร้างเพิ่มในอนาคต |

## 5.4 การออกแบบเพื่อความสะดวกในการใช้งาน (Usability: `NFR-USE-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) |
|---|---|
| NFR-USE-01 | **ภาษาต้องเป็นที่หนึ่ง:** ระบบและเอกสาร **จะต้อง** ออกแบบโดยเน้นภาษาไทยเป็นหลัก (Thai-first) ด้วยตัวอักษรที่มีความน่าเชื่อถือสูง อ่านง่าย (IBM Plex Sans Thai) |
| NFR-USE-02 | **เห็นการทำงานของ AI:** หน้าจอแชท **จะต้อง** แสดงแผงพาเนลถ่ายทอดสดสถานะการทำงานของบรรดา Agent ว่ากำลังคิดอยู่ตรงไหน ทำอะไรอยู่ ដើម្បីให้ผู้ใช้อดทนรอและเข้าใจกระบวนการทำงานที่ซับซ้อน |
| NFR-USE-03 | **ผลลัพธ์เชิงบวก:** ไม่มีการปล่อยให้สถานะ "ไม่มีข้อมูล" ลอยหน้าลอยตาเงียบๆ ระบบ **จะต้อง** แจ้งเหตุผลและแนะทางเลือกที่สามารถทำได้ให้ผู้ใช้เห็นอย่างชัดเจนเสมอ |
| NFR-USE-04 | **แนะนำเครื่องมือตลอดทาง:** กล่องเลือกเครื่องมือ (Tool selection) **จะต้อง** เห็นได้ชัดเจน มีคำอธิบายกำกับแต่ละหมวด เพื่อให้ผู้ใช้เลือกโหมดที่ถูกวัตถุประสงค์ที่สุด |

## 5.5 การบำรุงรักษาและการเข้าถึงข้อมูลเชิงวิศวกรรม (Maintainability & observability: `NFR-MNT-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) |
|---|---|
| NFR-MNT-01 | **บันทึกข้อผิดพลาดที่มีประโยชน์:** ปัญหาเกี่ยวกับ Agent **จะต้อง** ถูกแยกกลุ่มประเภทอย่างเป็นระบบ และเก็บคำอธิบายสภาพแวดล้อมโดยรอบ (prompt/step/type) เพื่อให้ง่ายต่อการดีบัก |
| NFR-MNT-02 | **หน้าจอ Swagger ยืนยันสุขภาพ:** ฝั่ง Backend **จะต้อง** เปิดเอกสาร Swagger (`/docs`) และพอยต์ตรวจสอบสุขภาพ (`/health`) ให้นักพัฒนาใช้งานติดตามอยู่เสมอ |
| NFR-MNT-03 (หนี้เทคนิค) | **หนี้ทางเทคนิคที่มีอยู่ (Tech debt):** สิ่งที่ต้องตามไปเก็บในอนาคตคือ การซ้ำซ้อนกันของรหัสโดเมนข้ามโมดูล, หน้าที่การทำงานที่ซ้อนทับกันของ Agents, การฮาร์ดโค้ดตั้งรายการรายชื่อของ Pipeline Agent ในโค้ด และปัญหาขาดการวางแผนระยะเวลาการเก็บรักษาไฟล์ `error_logs/` ในเครื่อง |

## 5.6 ความง่ายต่อการติดตั้งและนำไปใช้งานที่อื่น (Portability: `NFR-PORT-*`)

| รหัสอ้างอิง | คำอธิบายความต้องการ (Requirement) |
|---|---|
| NFR-PORT-01 | **รันจบด้วยคำสั่งเดียว:** ทั้งระบบ **จะต้อง** ถูกเรียกขึ้นมาให้พร้อมใช้งานได้ด้วยคำสั่ง `docker compose up` จากโฟลเดอร์ของ Frontend ได้เลย ซึ่งมันจะสั่งอิมเมจของ Backend ขึ้นมาและคุมบริการทั้งหมด 5 ตัวเองอัตโนมัติ |
| NFR-PORT-02 | **ข้อมูลสภาพแวดล้อมที่ตั้งค่าได้:** ตัวแปรที่มีผลต่อสภาพแวดล้อม (ตัวอย่าง โฮสต์ DB, IP ของ MinIO, กุญแจต่างๆ) **จะต้อง** โยนเข้าไปผ่าน env vars / หรือไฟล์ `.env` แทนที่จะฮาร์ดโค้ดฝังตายในตัวโค้ดหลัก |
